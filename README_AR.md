# النسر للتجارة — Al Nesr Trading

## الحالة الحالية للمشروع

المشروع يحتوي على نسختين مختلفتين من واجهة التطبيق:

- `preview/index.html`: الواجهة المطوّرة التي يجري العمل عليها واختبارها. تتصل بقاعدة بيانات الاختبار فقط.
- `app/`: الواجهة الأقدم الموجودة حاليًا خلف رابط التشغيل الرئيسي. لا تحذف هذا المجلد أو تستبدله قبل تنفيذ انتقال إنتاج مُراجع ومختبَر.

**تنبيه:** مجلد `preview/` ليس فرع Git مستقلًا؛ إنه مجلد داخل المستودع. روابط التشغيل وإعدادات GitHub Pages لم تتغير ضمن تنظيم الفروع الحالي.

## الفروع وطريقة العمل

- `main`: الفرع الرئيسي الحالي. لا تُجرَ عليه تعديلات تطويرية مباشرة.
- `development`: فرع العمل للتعديلات الجديدة واختبارها على Preview وقاعدة بيانات الاختبار.
- `backup-preview-2026-11-24`: نقطة استرجاع محفوظة من النسخة التي بدأنا منها التنظيم. لا تستخدمه للتطوير اليومي ولا تعدّل محتواه.

بدأت الفروع الثلاثة من نفس نقطة Git، ولذلك كانت ملفاتها متطابقة عند إنشائها. أي تعديل لاحق على `development` لا يغيّر الفرعين الآخرين تلقائيًا.

## خريطة الملفات والمجلدات

### `preview/`
- `index.html`: التطبيق المطوّر الحالي، ويحتوي الواجهة والتنسيقات والبرمجة في ملف واحد.
- إعداد الاتصال داخله موجّه إلى مشروع Supabase التجريبي. لا تنسخ إعداداته إلى الإنتاج.

### `app/`
- `index.html`: صفحة التطبيق الأقدم.
- `app.js`: منطق التطبيق الأقدم.
- `styles.css`: تنسيقات التطبيق الأقدم.
- `config.js`: إعداد اتصال نسخة الإنتاج.
- `README_AR.md`: توثيق النسخة الأقدم.

هذا المجلد ما زال مطلوبًا لمسار التشغيل الرئيسي الحالي، لذلك يُحتفظ به إلى أن يتم نقل الإنتاج بطريقة منفصلة ومختبرة.

### `supabase/`
يحتوي ملفات تأسيس قاعدة البيانات وتحديثاتها:
- `schema.sql`: البنية الأساسية الأولية.
- ملفات الترقية المرقّمة: تغييرات قاعدة البيانات المتتابعة، ويجب الحفاظ على ترتيبها وسجلها.
- `verify_setup.sql`: فحص هيكلي للمكونات المطلوبة، وليس بديلًا عن الاختبارات الوظيفية.

**لا تعِد تشغيل ملفات التأسيس أو الترقية عشوائيًا على قاعدة بيانات تحتوي بيانات فعلية.** راجع حالة قاعدة البيانات وسجل الترحيلات قبل أي تنفيذ. بعض ملفات الترقية قد تكون توثيقية أو لا تنفذ تغييرًا جديدًا، لكنها قد تكون لازمة لإعادة بناء التسلسل التاريخي.

### ملفات الجذر
- `index.html`: يحوّل الرابط الجذري حاليًا إلى `app/`.
- `manifest.json`: إعدادات تثبيت التطبيق كتطبيق ويب.
- `sw.js`: Service Worker لإدارة دورة حياة التخزين المؤقت القديم.
- `README_AR.md`: هذا الملف، لتوثيق بنية المشروع وطريقة العمل.

## قواعد السلامة والنشر

1. التطوير الجديد يكون على `development` فقط.
2. اختبر الواجهة على Preview وقاعدة بيانات الاختبار، ولا تستخدم بيانات إنتاج حقيقية للاختبار.
3. لا تغيّر مشروع Supabase الإنتاجي أو إعداداته أو بياناته دون موافقة صريحة.
4. لا تنقل كود Preview إلى مسار الإنتاج ولا تغيّر وجهة GitHub Pages قبل مراجعة إعدادات الاتصال والملفات واختبار النسخة المرشحة.
5. لا تحذف المجلدات أو ملفات SQL القديمة لمجرد أنها تبدو غير مستخدمة؛ تحقق أولًا من اعتماد التشغيل وسجل قاعدة البيانات عليها.
6. احتفظ بنسخة احتياطية قبل أي عملية نقل أو استبدال أو حذف.

## ملاحظة عن حالة الجاهزية

## خريطة الاعتماديات ومسارات التشغيل (مراجعة 24 نوفمبر 2026)

### النسخة المطوّرة `preview/index.html`
- ملف HTML واحد يضم الواجهة والتنسيقات ومنطق JavaScript؛ لا توجد ملفات CSS أو JS محلية منفصلة داخل `preview/`.
- تعتمد على مكتبة `@supabase/supabase-js` الإصدار الرئيسي 2 من CDN، مع رابط بديل من unpkg عند فشل تحميل jsDelivr.
- تعتمد على `xlsx` الإصدار 0.18.5 من CDN لعمليات ملفات Excel.
- إعداد Supabase التجريبي موجود داخل ملف الواجهة. لا تنقل هذا الإعداد إلى نسخة الإنتاج.
- لا يظهر في الملف ربط بملف `manifest.json` أو تسجيل لـ Service Worker.

### النسخة الأقدم `app/`
- `app/index.html` يحمّل `app.js` و`styles.css` و`config.js` من نفس المجلد.
- يحمّل `@supabase/supabase-js` الإصدار الرئيسي 2 و`xlsx` الإصدار 0.18.5 من CDN.
- `config.js` يحتوي إعداد اتصال Supabase الإنتاجي؛ لذلك لا تنشر أو تختبر هذه النسخة على أنها Preview.
- صفحة `app/index.html` تربط `../manifest.json`، وملف manifest يجعل `./app/` نقطة بدء التطبيق المثبّت.

### ملفات الجذر والنشر
- `index.html` يحوّل زائر الرابط الجذري إلى `./app/`.
- `manifest.json` مرتبط حاليًا بصفحة `app/`، وليس بصفحة Preview.
- `sw.js` موجود في المستودع، لكن المراجعة النصية للملفات الحالية لم تجد استدعاءً يسجّله عبر `navigator.serviceWorker.register`. لا نحذفه الآن؛ قد تكون له صلة بتثبيتات أو إصدارات سابقة ويحتاج قرارًا منفصلًا.
- قائمة الجذر الحالية لا تحتوي مجلد `.github/`، ولم يظهر Workflow نشر متعقب داخل المستودع. هذا لا يثبت وحده إعداد GitHub Pages الفعلي؛ إعدادات Pages نفسها لم تتغير ولم تُفحص من لوحة GitHub في هذه الخطوة.

### قرار التنظيف
هذه خريطة اعتماديات مبنية على قراءة الملفات الموجودة، وليست اختبار تشغيل كاملًا. لا يُحذف أي ملف أو مجلد بناءً عليها وحدها. يلزم أولًا وضع خطة انتقال منفصلة للرابط الرئيسي وPWA وإعدادات Supabase، ثم اختبارها قبل الاستغناء عن النسخة القديمة أو ملفات الجذر.


## مراجعة ملفات قاعدة البيانات (24 نوفمبر 2026)

تمت مراجعة ملفات SQL الموجودة في مجلد `supabase/` على فرع `development` قراءةً فقط، دون تشغيل SQL أو الاتصال بأي قاعدة بيانات أو تغيير بياناتها.

### خريطة الملفات

- `schema.sql`: ملف تأسيس البنية الأولية، وليس نسخة موحدة حديثة من كل التغييرات اللاحقة.
- `002` إلى `030`: سلسلة تغييرات تأسيسية وأمنية وتشغيلية؛ تفاصيلها موثقة جزئيًا في `supabase/README_AR.md`.
- `031` إلى `040`: تحديثات لاحقة كبيرة لمنطق عكس الفواتير والمدفوعات، توقيت وترتيب ترحيل الحركات والأقفال، أرصدة الأطراف، سلامة إعادة الضبط والاستعادة، المصروفات، ثم إضافة المدفوعات المستقلة للعملاء والموردين.
- `041` و`042` و`043`: ملفات no-op تحتوي `select 1;` وتذكر صراحةً أن التعديلات المقصودة مضمنة بالفعل في `040_standalone_party_payments.sql`. محتوى الملفات الثلاثة متطابق؛ الاحتفاظ بها يحافظ على تسلسل الترحيلات التاريخي، ولا يوجد مبرر لحذفها الآن.
- `044` إلى `050`: استكمال احتساب عكس المدفوعات المستقلة في التقارير، ترتيب إعادة الضبط، التحقق من نوع حساب الطرف وحالته، وإصلاحات/تحققات محددة لدوال المرتجعات والفواتير وإعادة الضبط.
- `051` و`052`: تحديثان متتابعان لدالة استعادة النسخ الاحتياطية؛ لا يصح اعتبارهما نسختين زائدتين لمجرد تشابه الحجم والبنية، لأن كل ملف يطوّر منطق الاستعادة.
- `053` إلى `055`: تقييد صلاحيات الإيداع والسحب اليدوي للكاشير، إصلاح تنبيهات المخزون واستعادة المنتجات، وضبط مرجع المدفوعات عند عكسها.
- `057_multi_account_deposits_withdrawals.sql`: إضافة تحديد حساب الحركة (الخزنة/وسائل الحساب الأخرى) ودوال الإيداع والسحب لكل حساب، مع إبقاء الحركات السابقة على القيمة الافتراضية `cash`.

### نقاط تحتاج الانتباه

1. **الرقم 056 غير موجود:** قائمة المجلد لا تحتوي ملفًا بهذا الرقم. كما أن سجل GitHub للملف بالمسار المتوقع لم يُظهر أي commit سابق له. لا يوجد دليل كافٍ يفسر سبب تخطي الرقم؛ لذلك لا نفترض أنه ملف محذوف أو migration ناقصة، ولا ننشئ ملفًا بديلًا من عندنا.
2. **توثيق Supabase الداخلي متأخر:** ملف `supabase/README_AR.md` يشرح التسلسل حتى Migration 030 فقط، ولا يوثق التغييرات من 031 إلى 057. يلزم تحديثه لاحقًا بعد مطابقة الملفات مع سجل الترحيلات الفعلي في قاعدة الاختبار.
3. **حدود ملف التحقق:** `verify_setup.sql` يذكر أنه يُشغّل بعد `schema.sql` وملفات 002 إلى 011، ويفحص وجود مكونات أساسية وسياسات محددة. لا يثبت وحده تطبيق أو سلامة جميع التغييرات من 012 إلى 057، ولا ينفذ سيناريوهات تشغيل فعلية.
4. **طريقة التنفيذ التاريخية مهمة:** توثيق Supabase الداخلي يذكر أن بعض التغييرات القديمة نُفذت يدويًا من SQL Editor وبعضها سُجل عبر أداة migrations. لذلك لا يكفي ترتيب أسماء الملفات أو وجودها للحكم على ما طُبق فعليًا في قاعدة الاختبار.
5. **لا حذف ولا إعادة تشغيل:** لا تُحذف ملفات no-op أو الملفات المتشابهة، ولا تُعاد migrations على قاعدة قائمة لمجرد ترتيب المجلد. يلزم أولًا مطابقة تعريفات قاعدة الاختبار وسجل `supabase_migrations.schema_migrations` مع كل ملف، دون إجراء أي تغيير.

هذه المراجعة تصنيف ساكن لمحتوى الملفات، وليست إثباتًا أن كل migration طُبقت على قاعدة الاختبار أو الإنتاج. لم يتم تعديل أي قاعدة بيانات، ولم يتم فحص قاعدة الإنتاج.


### مطابقة سجل قاعدة الاختبار مع ملفات المستودع

تمت قراءة سجل migrations الفعلي في مشروع `alnesr-trading-test` ومقارنته بأسماء ملفات `supabase/` على فرع `development`، دون تشغيل SQL أو تعديل القاعدة.

- سجل قاعدة الاختبار يحتوي على **111 migration مسجلة**.
- مجلد `supabase/` يحتوي على **55 ملف ترقية مرقمًا**، بالإضافة إلى `schema.sql` و`verify_setup.sql`.
- عند توحيد بادئة الترقيم ومقارنة الأسماء، تطابق 34 اسمًا من سجل القاعدة مع ملفات موجودة. أما بقية الأسماء فلا تُعد دليلًا تلقائيًا على فقدان ملفات؛ بعضها قد يكون نُفذ يدويًا أو سُجل باسم مختلف، ويحتاج مطابقة محتوى منفصلة.
- من المهم تصحيح ملاحظة الرقم 056: قاعدة الاختبار تسجل migration باسم `056_preserve_invoice_payment_cash_linkage` بتاريخ إصدار `20261117220446`، لكن لا يوجد ملف SQL مقابل لها في مجلد المستودع الحالي، ولم يظهر الملف أو اسمه في بحث GitHub داخل المستودع. لذلك نعرف أنها سُجلت كتطبيق في قاعدة الاختبار، لكن لا نملك مصدر SQL محفوظًا في الفرع الحالي لتدقيق محتواها.
- القاعدة تسجل أيضًا `057_multi_account_deposits_withdrawals`، والملف المقابل موجود في المستودع.
- ملف `schema.sql` يعرّف 16 جدولًا أساسيًا؛ جميعها موجودة في قاعدة الاختبار. وتحتوي القاعدة على 10 جداول إضافية لا ينشئها ملف التأسيس وحده، منها جداول ميزات لاحقة وجداول نسخ احتياطية للاختبار. لذلك لا يمثل `schema.sql` وحده الحالة الحالية الكاملة للقاعدة.
- ملف `verify_setup.sql` يعلن صراحةً أنه مخصص للتحقق بعد `schema.sql` والترقيات 002 إلى 011، فلا ينبغي استخدام نجاحه كدليل على سلامة جميع ترقيات التطبيق الحديثة.

**الاستنتاج:** سجل قاعدة الاختبار أوسع من مجموعة ملفات SQL الحالية. لا نحذف أو نعيد تسمية أو نعيد تشغيل أي ملف بناءً على هذه المقارنة. قبل اعتبار المستودع مصدرًا كاملًا لإعادة بناء قاعدة البيانات، نحتاج استعادة/توثيق ملفات التغييرات التي لا يوجد لها مصدر مطابق، ومراجعة الفروق الفعلية في تعريفات الجداول والدوال والـ views. هذه المطابقة لم تشمل قاعدة الإنتاج.


### جرد مكونات قاعدة الاختبار الحالية

في قراءة كتالوج قاعدة الاختبار فقط، بتاريخ 24 نوفمبر 2026، ظهرت الأعداد التالية داخل schema `public`:

- 26 جدولًا.
- 7 Views.
- 58 دالة.
- 17 Trigger غير داخلي.

وبالمقارنة النصية، يحتوي `schema.sql` على تعريف 16 جدولًا و3 دوال، ولا يحتوي تعريف Views. الجداول الأساسية الستة عشر كلها موجودة في قاعدة الاختبار، وتوجد مكونات إضافية جاءت من التحديثات اللاحقة. هذه أعداد للمكونات الموجودة وليست مقارنة كاملة لتعريف كل عمود أو جسم كل دالة أو شرط كل View/Trigger؛ لذلك لا تُستخدم وحدها لإثبات التطابق الكامل.


### تدقيق أعمق لسجل migrations غير المطابق (24 نوفمبر 2026)

أُعيدت قراءة سجل migrations في قاعدة الاختبار ومقارنته بأسماء ملفات SQL الحالية، ثم فُحص تاريخ GitHub للملفات ذات الصلة. هذه مراجعة قراءة فقط؛ لم يُنفّذ SQL ولم تُعدّل قاعدة البيانات.

- العدد ما زال **111 سجل migration** مقابل **55 ملف SQL مرقمًا** في المستودع.
- عند مقارنة الاسم بعد تجاهل البادئة الرقمية فقط، يوجد **34 سجلًا** لها اسم مطابق لملف حالي، و**77 سجلًا** لا يوجد لها تطابق مباشر بالاسم.
- توزّع السجلات الـ77 غير المطابقة حسب تاريخ الإصدار: 5 في 16 نوفمبر، و30 في 17 نوفمبر، و5 في 18 نوفمبر، و1 في 19 نوفمبر، و14 في 20 نوفمبر، و8 في 21 نوفمبر، و1 في 22 نوفمبر، و13 في 23 نوفمبر 2026.
- عدم التطابق بالاسم لا يثبت وحده فقدان 77 ملف SQL؛ سجل القاعدة يحتفظ باسم migration وقت تسجيلها، بينما قد تكون ملفات المستودع قد جُمعت أو أعيدت تسميتها أو وثّقت تغييرات متعددة في ملف واحد. كما يذكر هذا التوثيق أن بعض عمليات التأسيس القديمة و012 و014 نُفذت يدويًا من SQL Editor.
- في المقابل، لا يجوز اعتبار كل السجلات مغطاة بملفات حالية دون مقارنة محتوى كل تغيير على حدة. لذلك تبقى الملفات المصدرية لبعض التغييرات غير مثبتة.

- توجد مجموعات من تغييرات الفواتير والمرتجعات والخزنة والصلاحيات والرصيد الدائن بين 18 و23 نوفمبر لا تطابق أسماء ملفات SQL الحالية مباشرة. بعضها قد يكون نُفذ كترقيات منفصلة أو تغييرات لاحقة من SQL Editor/أداة migrations، لكن لا يوجد في المستودع الحالي ربط موثق واحد لواحد يثبت مصدر كل سجل.
- لم نستنتج محتوى أي migration من اسمها فقط، ولم نعتبر السجلات غير المطابقة تغييرات مفقودة مؤكدة.

**القرار الآمن:** لا نحذف ملفات SQL، ولا نعيد تسميتها، ولا نعيد تشغيل أي migration، ولا ننشئ ملفات 055/056 تخمينية. قبل اعتبار المستودع قابلًا لإعادة بناء قاعدة الاختبار بالكامل، يلزم استعادة مصادر SQL الأصلية أو توثيق الفروق من تعريفات قاعدة الاختبار الحالية ومراجعة كل مجموعة تغيير على حدة. لم يتم فحص قاعدة الإنتاج أو تعديلها.


### ربط بعض السجلات غير المطابقة بملفات المصدر الموجودة

استكمالًا للمراجعة، فُحص محتوى ملفات 031 إلى 039 وتاريخ Commit لكل ملف، ثم قورنت أوقات ورسائل التغييرات بسجل قاعدة الاختبار. ظهرت روابط قوية لبعض السجلات التي لا تتطابق أسماؤها حرفيًا:

- الملف 031 يعرّف مجموعة كبيرة من دوال عكس الفواتير وإعادة الضبط والاستعادة وواجهات أرصدة وكشوف الأطراف والتقارير. وتعليقه يذكر أنه يعكس تغييرات مطبقة بالفعل في قاعدة الاختبار؛ لذلك يبدو ملف تجميع/حفظ لحالة عدة تغييرات متقاربة، وليس بالضرورة مصدرًا واحدًا مقابل سجل واحد.
- الملفات 032 إلى 039 لها ارتباط واضح بمجموعات تغييرات في سجل 17 نوفمبر من حيث موضوع التغيير وتوقيت Commit، مثل توقيت ترحيل الحركات، وأقفال المخزون، وتسوية عكس المدفوعات، وترتيب الأقفال، وأرصدة المرتجعات، وإعادة الضبط والاستعادة، وسجل المصروفات والفهارس. هذه قرائن قوية على وجود مصدر محفوظ لبعض السجلات غير المطابقة، لكنها لا تثبت وحدها أن محتوى كل ملف هو النص الحرفي الذي نُفذ في القاعدة.
- سجل 046 اسمه قريب من الملف 046 الحالي مع اختلاف بسيط في ترتيب الكلمات؛ لذلك يُعامل كاختلاف تسمية محتمل، لا كدليل فقدان ملف.
- هذه الروابط تفسر لماذا لا يصح وصف السجلات الـ77 غير المطابقة بأنها 77 ملفًا مفقودًا. العدد 34 هو تطابق أسماء مباشر فقط؛ توجد حالات أخرى لها مصادر محتملة أو ملفات تجميع، وتظل المطابقة النهائية بالمحتوى غير مكتملة.

**ما بقي بلا مصدر SQL مباشر في المستودع بعد هذا الفحص:** سجلا 055_reverse_invoice_payment و056_preserve_invoice_payment_cash_linkage تحديدًا لا يوجد لهما ملف مطابق أو تاريخ Commit للمسارين المتوقعين. كما توجد سجلات أخرى من 18 إلى 23 نوفمبر لا يظهر لها ملف SQL منفصل مطابق في المجلد الحالي؛ لم نثبت بعد إن كانت مغطاة داخل ملفات أخرى أو نُفذت خارج المستودع. لا نعتبرها مفقودة بشكل نهائي قبل مقارنة محتوى تعريفات القاعدة وتاريخ كل تغيير.


### فحص شامل لمواضع ملفات SQL في المستودع

تم فحص شجرة ملفات فرع development كاملة، وليس مجلد supabase فقط. جميع ملفات SQL الموجودة حاليًا تقع داخل supabase/؛ لا توجد ملفات migrations بديلة في مجلد آخر. أحدث ملف ترقية مرقم هو 057_multi_account_deposits_withdrawals.sql، وتاريخ إضافته 20 نوفمبر 2026. فُحص محتواه وتأكد أنه خاص بحركات الإيداع والسحب متعددة الحسابات، ولا يحتوي تغييرات سجل ائتمان العملاء أو ائتمان الموردين.

بناءً على ذلك، لا توجد في نسخة المستودع الحالية ملفات SQL مستقلة للتغييرات المسجلة بين 18 و23 نوفمبر مثل رصيد العميل الدائن وتسويته، والرصيد المؤجل للمورد وتسويته، وطرق رد المرتجعات، وعدد من إصلاحات الخزنة والصلاحيات. هذا يؤكد غياب ملفات منفصلة مطابقة لهذه السجلات من شجرة المستودع الحالية، لكنه لا يحدد وحده طريقة تنفيذها أو ما إذا كان بعضها قد دُمج في SQL نُفذ خارج المستودع. لا تُنشأ ملفات بديلة اعتمادًا على أسماء السجلات؛ يلزم استعادة SQL الأصلي أو توثيق تغييرات القاعدة بدقة قبل اعتبار المستودع مصدرًا كاملًا لإعادة البناء.


### مراجعة كتالوج قاعدة الاختبار للتغييرات اللاحقة (قراءة فقط)

للتأكد من أن التغييرات التي لا تملك ملفات SQL منفصلة موجودة فعلًا في قاعدة الاختبار، تمت قراءة أعمدة الجداول وتعريفات Views وسياسات RLS وامتيازات الجداول وبيانات RPC من كتالوج PostgreSQL فقط.

- جدول customer_credit_ledger موجود، ويحتوي على روابط العميل ومرتجع المصدر والفاتورة والدفعة ونوع الحدث والمبلغ ومرجع عكس القيد.
- جدولا purchase_returns وpurchase_return_items موجودان، وكذلك treasury_transfers. وتظهر أعمدة مرتجع المورد حقولًا مثل posted_at وstatus وcredit_generated_total وinvoice_due_reduced_total.
- RLS مفعّل على الجداول الأربعة customer_credit_ledger وpurchase_returns وpurchase_return_items وtreasury_transfers. السياسات المقروءة مخصصة لدور authenticated وتسمح بالقراءة وفق صلاحيات النشاط المناسبة: sales.view/parties.view لسجل ائتمان العميل، وpurchases.view لمرتجعات المورد، وpayments.view لتحويلات الخزنة.
- لا يملك authenticated صلاحيات INSERT أو UPDATE أو DELETE المباشرة على هذه الجداول؛ عمليات التغيير تمر عبر RPC. توجد صلاحية SELECT لـanon على بعض الجداول الثلاثة الأخيرة، لكن لا توجد لها سياسة RLS موجهة إلى anon، وRLS مفعّل؛ لذلك لا تعني صلاحية الجدول وحدها إمكانية قراءة الصفوف.
- العرضان customer_credit_balances وcustomer_credit_return_balances موجودان ومضبوطان بـsecurity_invoker=true، وكذلك party_account_balances وparty_account_statement؛ وهذا يجعل الوصول للصفوف خاضعًا لصلاحيات وسياسات الجداول الأساسية.
- ظهرت دوال RPC ذات صلة بالميزات، منها pay_customer_credit وreceive_supplier_credit وpost_purchase_return_with_settlement وpost_purchase_with_method وowner_void_purchase_return. الدوال التي فُحصت لهذه المجموعة SECURITY DEFINER، ولها search_path مضبوط، ولا تملك anon صلاحية EXECUTE، بينما authenticated يملك EXECUTE. ظهر auth.uid() في أجسام الدوال المفحوصة، باستثناء النسخة القديمة ذات التسعة معاملات من post_sale_with_method؛ وهذه هي الواجهة القديمة التي سبق تحديدها كـwrapper يستدعي النسخة الأحدث ذات فحص الصلاحيات، وليست دليلًا منفردًا على ثغرة.

هذه النتائج تؤكد وجود أجزاء مهمة من الميزات اللاحقة في قاعدة الاختبار، وتوضح أن الوصول المباشر للكتابة مقيد. لكنها لا تستعيد نصوص migrations الأصلية ولا تثبت تطابق كل جسم دالة مع الملف الذي ربما استُخدم وقت التنفيذ. لم يتم إدخال أي بيانات أو تعديل أي صلاحية أو بنية، ولم يتم فحص قاعدة الإنتاج.


### مقارنة أسماء أعمدة schema.sql مع قاعدة الاختبار

تمت مقارنة أسماء الأعمدة في الجداول الأساسية الستة عشر التي يعرّفها schema.sql مع information_schema.columns في قاعدة الاختبار. جميع أعمدة الجداول الأساسية موجودة؛ لم يظهر عمود أساسي مفقود بالاسم. لكن قاعدة الاختبار تحتوي **35 عمودًا إضافيًا** غير موجود في ملف التأسيس الأولي:

- businesses: tagline.
- parties: opening_balance_side, is_active, party_code.
- purchase_invoices: paid_total, due_total, status, supplier_credit_applied_total.
- sales_invoices: customer_credit_applied_total.
- payments: sales_return_id, reversal_of_payment_id, posted_at, party_account_type, payment_code, purchase_return_id.
- stock_movements: reversal_of_movement_id, posted_at, movement_code, stock_bucket.
- sales_returns: status, posted_at, invoice_due_reduced_total.
- sales_return_items: unit_price.
- expenses: cash_transaction_id, status, voided_at, voided_by, expense_code.
- cash_transactions: reversal_of_transaction_id, sales_return_id, payment_id, treasury_transfer_id, transaction_code, account_method, purchase_return_id.

أما business_members وproducts وpurchase_items وsales_items وbusiness_settings وaudit_log، فلم يظهر اختلاف في أسماء الأعمدة ضمن هذه المقارنة.

هذه مقارنة لأسماء الأعمدة فقط؛ لم تثبت تطابق أنواع البيانات أو القيود أو القيم الافتراضية أو الفهارس أو سياسات RLS أو أجسام الدوال. لكنها تؤكد أن schema.sql ليس نسخة كاملة حديثة من بنية قاعدة الاختبار، ولا ينبغي استخدامه وحده لإعادة إنشاء القاعدة الحالية.

### مراجعة صلاحيات العمليات المالية والمخزنية (24 نوفمبر 2026)

تمت مراجعة تعريفات دوال RPC المتاحة لدور authenticated في قاعدة الاختبار، مع قراءة أجزاء من واجهة Preview على فرع development لمقارنة صلاحيات الواجهة بشروط قاعدة البيانات. جميع الاستعلامات كانت قراءة فقط؛ لم تُنفذ أي عملية مالية أو مخزنية، ولم تُغيّر أي صلاحية أو بيانات.

#### ما ظهر في المراجعة

- الدوال الأساسية التي تمت مراجعتها لإنشاء المبيعات والمشتريات والمرتجعات والمدفوعات وحركات الخزنة وتسويات المخزون تتحقق من هوية المستخدم النشطة، وتستخدم صلاحيات النشاط المناسبة عبر `has_business_permission`، أو تقصر العملية على المالك النشط في عمليات الإلغاء والعكس والإدارة الحساسة.
- صلاحيات تنفيذ الدوال التي شملها الجرد لا تسمح لدور `anon` بالتنفيذ؛ التنفيذ متاح لـ`authenticated`. وجود `SECURITY DEFINER` وحده لا يعني وجود ثغرة، ويجب تقييم كل دالة مع شروطها الداخلية.
- نسخة `post_sale_with_method` القديمة ذات 9 معاملات لا تحتوي فحص هوية مستقلًا في جسمها، لكنها Wrapper تستدعي النسخة ذات 10 معاملات التي تحتوي فحص الصلاحية. لم يظهر من هذا الفحص أنها تتجاوز الحماية.
- دوال الإلغاء وعكس المدفوعات والتعديلات الحساسة التي فُحصت تقصر التنفيذ على المالك النشط.
- دالة إنشاء مرتجع المبيعات تتحقق من `sales.create`، وتطلب أيضًا `cash.withdraw` عندما يتضمن المرتجع ردًا نقديًا. دوال الإيداع والسحب والتسجيل المالي تتحقق من صلاحياتها المقابلة.

#### ملاحظة صلاحيات تحويل الأرصدة للكاشير — تحتاج قرارًا

- الإعدادات الافتراضية لدور `cashier` في الواجهة تتضمن `cash.create` و`cash.view` و`payments.view`.
- واجهة تحويل الأرصدة تتحقق من هذه الصلاحيات، ودالتا `create_treasury_transfer` و`reverse_treasury_transfer` تستخدمان صلاحيات إنشاء حركة الخزنة/عرض المدفوعات للسماح بالتحويل وعكسه.
- النتيجة: الكاشير الافتراضي يستطيع إنشاء تحويل بين حسابات الخزنة وعكس التحويل، حتى دون امتلاك صلاحية `cash.deposit` أو `cash.withdraw`. هذا ليس تجاوزًا لقاعدة الصلاحيات؛ بل هو السلوك الذي تسمح به الصلاحيات الحالية.
- **التوصية المؤجلة:** مراجعة ما إذا كان تحويل الأرصدة وعكسه يجب أن يكونا للمالك/المدير فقط، أو يحتاجان صلاحية مستقلة بدل الاعتماد على `cash.create` و`payments.view`. لا تغيّر صلاحيات الأدوار أو الدوال قبل الاتفاق على القرار.

#### حدود ما تم التحقق منه

- هذه مراجعة ساكنة لتعريفات الدوال وبعض شروط الواجهة، وليست اختبارًا عمليًا بحسابات owner وmanager وcashier وviewer.
- قاعدة الاختبار وقت المراجعة تحتوي حساب مالك واحدًا فقط؛ لذلك يلزم اختبار الأدوار المتعددة لاحقًا بعد تجهيز حسابات اختبار مناسبة وبطريقة لا تمس بيانات فعلية.
- لم تُراجع بعد كل مسارات قراءة البيانات والتقارير والتصدير، ولم يُحسم بعد تطابق كل مفاتيح الصلاحيات في الواجهة مع كل RPC وسياسات RLS.

**حالة البند:** نتيجة التدقيق موثقة. لا يوجد إصلاح معتمد أو منفذ حتى الآن. تبقى مراجعة صلاحيات تحويل الأرصدة، واختبار الأدوار المتعددة، واستكمال تدقيق القراءة والتقارير ضمن قائمة ما بعد المراجعة.


### مراجعة صلاحيات قراءة البيانات والتقارير والتصدير (24 نوفمبر 2026)

تمت مراجعة سياسات RLS وامتيازات القراءة وتعريفات Views في قاعدة الاختبار، ثم مقارنة مسارات التقارير والتصدير في `preview/index.html` على فرع development. الفحص كان قراءة فقط، ولم تُنفذ أي عملية تغيير أو اختبار بحساب موظف فعلي.

#### ما ظهر في قاعدة البيانات

- RLS مفعّل على جميع جداول public التي شملها الفحص (26 جدولًا).
- كل Views السبعة مضبوطة بـ`security_invoker=true`: `cash_balances` و`customer_credit_balances` و`customer_credit_return_balances` و`daily_business_summary` و`party_account_balances` و`party_account_statement` و`product_stock_balances`. لذلك تُطبّق سياسات RLS للجداول الأساسية عند القراءة من هذه العروض، ولا تعمل كنافذة تتجاوز سياسات الجداول.
- سياسات قراءة الفواتير والبنود والمرتجعات والمخزون والمصروفات والخزنة تربط الصفوف بصلاحيات النشاط مثل `sales.view` و`purchases.view` و`inventory.view` و`expenses.view` و`cash.view`.
- قراءة الدفعات أكثر تقييدًا: تحتاج `payments.view`، ثم تتحقق من صلاحية المبيعات أو المشتريات المناسبة حسب الفاتورة أو نوع حساب الطرف. الدفعات غير المرتبطة بفاتورة أو طرف محدد محصورة في owner/admin.
- قراءة سجل الائتمان الخاص بالعميل تتطلب `sales.view` أو `parties.view`. ولقطات تكلفة المشتريات وتسويات المخزون محصورة في المالك.
- ظهرت صلاحية SELECT لـanon على عدد من الجداول والعروض، كما أن بعض السياسات معرفة لدور `public`. لكن شروط القراءة تعتمد على دوال العضوية والصلاحية التي تربط المستخدم بـ`auth.uid()` وعضويته النشطة؛ لذلك لا تعني صلاحية الجدول وحدها أن الزائر غير المسجل يستطيع قراءة صفوف النشاط. لم يُجر اختبار اتصال فعلي بدور anon في هذه المراجعة.
- لم يظهر في التعريفات المقروءة مسار واضح يعرض صفوف نشاط آخر؛ السياسات تستخدم `business_id` مع تحقق العضوية/الصلاحية. وتضيف الواجهة أيضًا فلتر `business_id=activeBusinessId` في استعلامات التقارير. هذا استنتاج من السياسات والكود، وليس اختبارًا عمليًا بين نشاطين بحسابين مختلفين.

#### ملاحظات تحتاج قرارًا أو ضبطًا

1. **اختلاف شرط قراءة تحويلات الخزنة بين قاعدة البيانات والواجهة — يحتاج قرارًا.**
   - سياسة RLS على `treasury_transfers` تسمح بالقراءة عند امتلاك `payments.view` فقط.
   - واجهة Preview لا تعرض قسم التحويلات ولا تطلب بياناته إلا عند امتلاك `cash.view` و`payments.view` معًا.
   - لذلك يستطيع مستخدم يملك `payments.view` دون `cash.view` قراءة سجلات التحويلات مباشرة عبر Data API، رغم أن الواجهة تخفي القسم عنه.
   - لا نعتبر هذا تسريبًا مؤكدًا قبل حسم معنى الصلاحيتين: هل التحويلات جزء من عرض المدفوعات، أم يجب أن تتطلب صلاحية الخزنة أيضًا؟ التوصية توحيد شرط RLS والواجهة بعد اعتماد القرار.

2. **اختلاف شرط إظهار صافي الربح عن شرط تصديره — عدم اتساق في الواجهة.**
   - شاشة التقارير تحسب وتعرض صافي الربح عند امتلاك `sales.view` و`expenses.view` و`inventory.view`.
   - تصدير Excel يشترط الصلاحيات الثلاث نفسها بالإضافة إلى `purchases.view`.
   - دالة الحساب نفسها تعتمد في مكوناتها على بيانات المبيعات والمرتجعات وحركات المخزون والمصروفات، ولا تقرأ إجمالي فواتير المشتريات مباشرة.
   - النتيجة أن المستخدم قد يرى صافي الربح في الشاشة ولا يجد ورقة صافي الربح في ملف Excel. يلزم توحيد الشرطين بعد مراجعة قرار من يحق له رؤية هذا المؤشر.

3. **كشوف حساب الأطراف — لا يظهر تجاوز في المسار المفحوص.**
   - الواجهة لا تحمل كشف الحساب الكامل في التقارير إلا عند امتلاك صلاحيات الأطراف والمبيعات والمشتريات والمدفوعات معًا.
   - العرض نفسه `security_invoker=true`، والجداول الأساسية تظل خاضعة لسياساتها؛ لذلك لا يُفترض أن الاستعلام المباشر عن العرض يتجاوز صلاحيات كل جدول. يلزم اختبار أدوار فعلي للتأكد من شكل النتائج الجزئية.

#### حدود الفحص

- لم تُنشأ حسابات cashier أو manager أو viewer ولم تُجر اختبارات API فعلية بهذه الأدوار؛ قاعدة الاختبار المعروفة وقت المراجعة تضم حساب مالك واحدًا.
- لم يُنفذ اختبار عزل بين نشاطين مستقلين بحسابين مختلفين.
- لم تُجر تجربة فعلية لدور anon أو anonymous sign-in؛ التقييم مبني على RLS ودوال التحقق المقروءة.
- لم نعتبر منح SELECT لـanon أو تعريف policy إلى `public` ثغرة تلقائيًا؛ يلزم تقييم predicate الفعلي وسياق المصادقة.
- لم تتغير الواجهة أو سياسات RLS أو بيانات قاعدة الاختبار أو قاعدة الإنتاج.

**حالة البند:** نتائج مراجعة القراءة والتقارير موثقة. لا يوجد إصلاح معتمد أو منفذ حتى الآن. البنود التي تحتاج قرارًا هي صلاحية قراءة تحويلات الخزنة، وتوحيد شرط صافي الربح بين الشاشة وExcel، ثم اختبار الأدوار وعزل الأنشطة عمليًا.


#### عيب برمجي إضافي في تصدير Excel — يحتاج إصلاحًا

أثناء تتبع ترتيب تنفيذ `exportReportsExcel()` ظهر عيب ساكن مؤكد في ترتيب تعريف المتغيرات:
- فرع تصدير ملخص حركة الأموال يستدعي `buildOperatingMoneyRows(..., from, to)` قبل تعريف `const from` و`const to` داخل الدالة.
- تعريف المتغيرين يأتي لاحقًا في نفس النطاق، ولذلك يؤدي الوصول إليهما قبل التهيئة إلى `ReferenceError` بسبب JavaScript Temporal Dead Zone.
- الأثر المتوقع: عند حساب يملك `cash.view` و`payments.view`، يتوقف تصدير Excel عند الوصول إلى هذا الجزء بدل إكمال الملف. هذا ينطبق على المالك وفق الصلاحيات الافتراضية.
- لم نشغّل التصدير فعليًا؛ النتيجة مستخلصة من ترتيب الكود، ولا نعتبرها اختبار تشغيل.
- الإصلاح المقترح عند بدء مرحلة التنفيذ: قراءة `from` و`to` في بداية `exportReportsExcel()` قبل أي استخدام، ثم اختبار التصدير لحساب مالك وحسابات بصلاحيات أقل.

**حالة البند:** عيب برمجي مؤكد من قراءة الكود، لم يُصلح بعد ولم يتم تعديل Preview.


### مراجعة إعدادات النشاط وسجل المراجعة وصور المنتجات (24 نوفمبر 2026)

تم فحص جداول `businesses` و`business_settings` و`audit_log`، وسياسات RLS وامتيازات الكتابة، وسياسات Storage لصور المنتجات، ثم تتبع مسارات الواجهة في `preview/index.html`. قاعدة الاختبار فقط، قراءة بيانات وتعريفات دون تنفيذ عمليات كتابة.

#### إعدادات النشاط

- بيانات النشاط الفعلية التي تعرضها الواجهة وتحفظها هي أعمدة جدول `businesses` (الاسم والهاتف والعنوان والشعار النصي).
- قراءة النشاط محصورة بعضوية النشاط عبر `is_business_member(id)`، والتعديل محصور في `owner/admin` عبر `has_business_role` في RLS. والواجهة تتحقق كذلك من دور owner/admin قبل التحديث.
- جدول `business_settings` منفصل ويحتوي JSONB، وسياساته تستخدم `settings.view/create/edit/delete` مع RLS. لكن الواجهة الحالية لا تستخدمه في شاشة إعدادات النشاط، كما أن خيارات صلاحيات الموظفين لا تعرض صلاحيات create/edit/delete للإعدادات. يبدو أنه مسار غير مستخدم حاليًا أو مخصص لتوسعة مستقبلية؛ لا نحذفه ولا نغيره قبل معرفة سبب وجوده.
- لا توجد صلاحيات كتابة مباشرة لـanon أو authenticated على الجداول الأربعة التي فُحصت (businesses, business_settings, audit_log, products)؛ الكتابة المباشرة تتم عبر مسارات RLS/RPC المسموح بها، وليس عبر منح SQL مباشر على الجدول.

#### سجل المراجعة audit_log

- الجدول محمي بـRLS، والقراءة تتطلب `audit.view` للنشاط المحدد. لا توجد صلاحيات INSERT/UPDATE/DELETE مباشرة لـanon أو authenticated، ولا توجد سياسات كتابة مباشرة.
- لم نعثر على شاشة أو وحدة في Preview تعرض سجل المراجعة للمستخدم، رغم وجود خيار `audit.view` في إعداد صلاحيات الموظفين. لذلك الصلاحية موجودة في قاعدة البيانات وخيارات الموظفين، لكن تجربة عرض السجل داخل الواجهة غير ظاهرة في الكود الحالي.
- السجل يحتوي بالفعل على أحداث من عمليات الاختبار، منها إنشاء الفواتير والمرتجعات والدفعات وتحويلات الخزنة وبعض عمليات الإلغاء والأرصدة الافتتاحية.
- التغطية ليست شاملة: بمقارنة الدوال التي تكتب في `audit_log` مع بقية عمليات الكتابة ومراجعة المشغلات، لم يظهر تسجيل مباشر في السجل لعمليات مثل تسجيل المصروف، السحب النقدي، الإيداع النقدي العام، وتسويات المخزون. ولا توجد مشغلات تدقيق عامة على جداول المصروفات أو حركات الخزنة أو حركات المخزون. قد تكون بعض هذه العمليات موثقة في سجلاتها التشغيلية الأخرى، لكنها لا تظهر في سجل المراجعة المركزي.
- **توصية:** اعتماد قائمة أحداث إلزامية لسجل المراجعة (من نفذ، ماذا فعل، على أي سجل، ومتى)، ثم استكمال التغطية وإضافة شاشة قراءة مقيدة بالصلاحية. لا نضيف تسجيلًا عامًا آليًا قبل تحديد البيانات التي يجب ألا تُنسخ إلى تفاصيل السجل.

#### صور المنتجات والتخزين

- Bucket `product-images` خاص (Private)، وحد الحجم 5MB، وأنواع الملفات المسموحة JPEG/PNG/WebP. لا توجد قراءة عامة؛ الواجهة تنشئ روابط موقعة لمدة ساعة بعد تحميل المنتجات.
- سياسات Storage تسمح بالقراءة لمن لديه `products.view` في النشاط الموجود في أول مجلد من مسار الملف، والرفع لمن لديه `products.create` أو `products.edit`، والتعديل لمن لديه `products.edit`.
- مسار الواجهة الحالي هو `business_id/product_id/random_uuid.ext`، ويتحقق من نوع الصورة وحجمها قبل الرفع. وسياسة التخزين تتحقق من وجود المجلد الثاني، لكنها لا تتحقق من أن UUID الموجود في المجلد الثاني يشير فعلًا إلى منتج تابع للنشاط نفسه، ولا تتحقق من أن الملف مرتبط بمنتج قائم. هذا لا يتيح تجاوز حدود النشاط الأول، لكنه يسمح لمستخدم مخوّل برفع ملفات يتيمة أو بمجلد منتج غير مطابق؛ وهي مشكلة اتساق/تنظيف أكثر من كونها كشفًا لصور نشاط آخر.
- سياسة حذف الصورة تسمح لمن لديه `products.edit`، أو لمالك الملف إذا كان لديه `products.create`. يجب مراجعة هذه القاعدة مع سلوك الواجهة عند حذف منتج أو تغيير صورته، خصوصًا أن حذف الصورة القديمة يتم بعد نجاح تحديث المنتج.
- لم نعثر في هذه المراجعة على سياسة عامة أو رابط عام يكشف صور المنتجات. ولم نجر اختبارًا فعليًا لروابط signed URL أو لحسابين من نشاطين مختلفين.

#### تصنيف النتائج

1. **مشكلة وظيفية مؤكدة من قراءة الواجهة:** خيار `audit.view` موجود لكن لا تظهر شاشة لعرض سجل المراجعة في Preview.
2. **نقص تغطية مؤكد في سجل المراجعة المركزي:** بعض عمليات الكتابة المهمة لا تسجل حدثًا فيه بحسب تعريفات الدوال والمشغلات الحالية.
3. **نقطة تصميم/تنظيف:** سياسة الصور لا تربط المجلد الثاني بمنتج قائم تابع للنشاط، وقد تسمح بملفات يتيمة لمستخدم مخوّل.
4. **لا توجد ثغرة كشف عامة مثبتة:** bucket خاص وروابط الصور موقعة وسياسات القراءة مقيدة بعضوية وصلاحية النشاط.
5. **غير محسوم:** الغرض المستقبلي من `business_settings`، واختبار عزل الصور والإعدادات والسجل عمليًا بحسابات متعددة.

**حالة البند:** النتائج موثقة للمراجعة اللاحقة فقط. لم تتغير سياسات RLS أو Storage، ولم تتغير الواجهة أو بيانات الاختبار أو الإنتاج.


### مراجعة دورة حياة عضوية الموظفين والجلسات (24 نوفمبر 2026)

تمت مراجعة تعريفات `add_business_member_by_email` و`update_business_member` و`list_business_members` وtrigger `guard_business_member_changes`، ودوال التحقق من العضوية والصلاحيات، ومسار تسجيل الدخول وتحميل مساحة العمل في Preview. الفحص على Test DB وتعريفات الكود فقط؛ لم يتم إنشاء مستخدمين أو تعديل عضويات أو إبطال جلسات.

#### ما يعمل بشكل سليم في التعريفات

- إضافة الموظف محصورة في مالك نشط، وتبحث عن حساب موجود وبريد مؤكد، وتسمح بالأدوار manager/cashier/viewer فقط، وتمنع تكرار العضوية.
- عرض قائمة الموظفين محصور في مالك نشط.
- تعديل الدور أو التفعيل أو الصلاحيات محصور في مالك نشط، مع قائمة مفاتيح صلاحيات مسموح بها وقيم Boolean فقط.
- لا يمكن عبر دالة التعديل تحويل عضو إلى owner/admin أو تعديل عضوية owner/admin؛ هذه العضويات محمية.
- Trigger يمنع تغيير هوية العضوية (business_id/user_id)، ويحمي تعيين/تعديل/حذف owner/admin، ويمنع إزالة أو تعطيل آخر مالك نشط.
- دوال `has_business_permission` و`has_business_role` و`is_business_member` تفحص العضوية النشطة في قاعدة البيانات في كل استدعاء. ودوال الإدارة متاحة لـauthenticated فقط وليست anon.
- قاعدة الاختبار وقت الفحص تحتوي مالكًا واحدًا نشطًا فقط، ولا تحتوي حسابات manager/cashier/viewer أو عضويات موقوفة؛ لم يمكن اختبار الأدوار عمليًا.

#### الملاحظة الأساسية: الجلسة المفتوحة بعد إيقاف العضوية

- واجهة Preview تحمّل العضويات النشطة عند تسجيل الدخول/تحديث مساحة العمل، وتحتفظ بنسخة منها في ذاكرة الصفحة. لم يظهر فحص دوري أو اشتراك Realtime يعيد تحميل العضوية عند تغييرها من جهاز آخر.
- عند تعطيل عضوية الموظف، دوال RLS والتحقق في قاعدة البيانات ستمنع طلباته الجديدة التي تعتمد على `has_business_permission` أو `is_business_member` بعد أن تصبح حالة العضوية غير نشطة.
- لكن واجهة الموظف المفتوحة قد تحتفظ مؤقتًا بعناصر القائمة والصلاحيات القديمة، وقد تظل البيانات التي سبق تحميلها ظاهرة في الصفحة/ذاكرة المتصفح حتى إعادة التحميل أو تسجيل الخروج. لا يوجد في الكود المفحوص مسار واضح يمسح هذه الحالة فورًا عند تعطيل العضوية من جهاز آخر.
- هذا لا يثبت أن الموظف يستطيع تنفيذ عمليات جديدة بعد التعطيل؛ حماية قاعدة البيانات تمنع ذلك في المسارات التي تستخدم فحوص العضوية. لكنه نقص في تحديث واجهة المستخدم ومسح البيانات المحلية المعروضة.

#### جلسات Supabase نفسها

- تعطيل صف العضوية في `business_members` ليس هو نفسه إبطال جلسة Supabase أو حذف access/refresh tokens. لا تستدعي واجهة إدارة الموظفين `auth.admin` أو revoke/sign-out لمستخدم آخر، ولا يوجد مسار ظاهر لإبطال كل جلساته.
- لذلك لا ينبغي وصف التعطيل بأنه تسجيل خروج فوري من كل الأجهزة. الضمان الموجود حاليًا هو رفض العمليات الجديدة المحمية بفحوص العضوية النشطة، وليس الإبطال الفوري للتوكن أو إزالة ما سبق عرضه.
- لحسم ضمان فوري أقوى مستقبلًا، يلزم تصميم آلية session/version أو تحقق خادمي من الجلسة على العمليات الحساسة، مع تحديث/مسح واجهة العميل عند اكتشاف التعطيل. لا نغيّر صلاحية الجلسات أو إعدادات Auth قبل تصميم واختبار أثر ذلك.

#### تصنيف البنود

1. **حماية قاعدة البيانات موجودة:** العضوية غير النشطة لا تجتاز helpers الأساسية التي تعتمد عليها سياسات RLS.
2. **نقص واجهة مؤكد من قراءة الكود:** لا يوجد تحديث دوري ظاهر لحالة العضوية ولا مسح فوري للبيانات المعروضة عند تعطيلها من جلسة أخرى.
3. **حدّ أمني يجب توضيحه:** تعطيل العضوية لا يساوي إبطال جلسة Supabase؛ لم يظهر إبطال لجلسات المستخدم الأخرى.
4. **اختبار عملي مطلوب:** إنشاء حساب موظف لكل دور، إبقاء جلسة مفتوحة على جهاز، تعطيل العضوية من حساب المالك، ثم اختبار طلبات القراءة والكتابة والتأكد من اختفاء البيانات/تسجيل الخروج أو إعادة التوجيه حسب السلوك المعتمد.
5. **حماية المالك:** trigger يمنع فقدان آخر مالك نشط، ولم يتم اختبار هذا السيناريو عمليًا.

**حالة البند:** الملاحظات موثقة للمراجعة اللاحقة. لم تتغير عضويات Test DB أو إعدادات Auth أو الجلسات أو ملفات التطبيق أو قاعدة الإنتاج.


### مراجعة تسجيل الدخول وإنشاء الحساب واستعادة كلمة المرور (24 نوفمبر 2026)

- نص الواجهة يوضح أن إنشاء الحساب وحده لا يمنح الوصول لأي نشاط، وأن الموظف يحتاج تأكيد البريد ثم إرسال بريده للمالك لإضافته.
- دالة إضافة الموظف تتحقق من وجود المستخدم في `auth.users` ومن أن `email_confirmed_at` غير فارغ، ولا تسمح بإضافة بريد غير مؤكد.
- لا يوجد في الواجهة مسار `resetPasswordForEmail` أو `updateUser` أو معالجة `PASSWORD_RECOVERY`؛ أي لا توجد شاشة «نسيت كلمة المرور» أو تغيير كلمة المرور أو إعادة إرسال تأكيد البريد في Preview حاليًا.
- إعداد عميل Supabase يستخدم `persistSession: true` و`autoRefreshToken: true` و`detectSessionInUrl: true`. ويعالج التطبيق أحداث INITIAL_SESSION وSIGNED_IN وSIGNED_OUT لعرض مساحة العمل أو شاشة الدخول.
- لا يوجد في `auth.users` trigger مخصص في Test DB، ولم تظهر دوال عامة مخصصة للتسجيل أو إعادة تعيين كلمة المرور.
- سياسات `business_members`: المستخدم المسجل يستطيع قراءة صف عضويته هو فقط؛ عمليات INSERT/UPDATE/DELETE المباشرة تتطلب دور owner النشط. قائمة الموظفين الكاملة تُجلب عبر RPC مخصصة تتحقق من المالك.
- حساب الاختبار الوحيد مؤكد البريد (1 مستخدم مؤكد، ولا يوجد مستخدم غير مؤكد). لذلك لم نختبر تدفق التأكيد الحقيقي أو رسائل البريد على حساب تجريبي منفصل.

#### ما لم يمكن التحقق منه من الكود وقاعدة البيانات

إعدادات Supabase Auth على مستوى المشروع غير متاحة في واجهة الفحص المستخدمة، لذلك لم نؤكد:
- هل تأكيد البريد الإلكتروني إلزامي في إعدادات المشروع أم لا.
- إعدادات SMTP وقوالب رسائل التأكيد والاستعادة.
- قائمة Redirect URLs المسموح بها، ووجهة العودة بعد تأكيد البريد أو استعادة كلمة المرور.
- الحد الأدنى الفعلي لكلمة المرور وسياسات كلمات المرور المسربة/الحماية الإضافية.
- حدود محاولات الدخول والتسجيل ومعدلات إرسال رسائل البريد.

لا نفترض أن هذه الإعدادات مضبوطة أو غير مضبوطة دون قراءة إعدادات Auth نفسها.

#### التصنيف والتوصيات

1. **سليم من ناحية فصل الحساب عن العضوية:** التسجيل لا يمنح عضوية تلقائية، وإضافة الموظف تتطلب بريدًا مؤكدًا وقرارًا من المالك.
2. **نقص وظيفي مؤكد في Preview:** لا توجد واجهة لاستعادة كلمة المرور أو تغييرها أو إعادة إرسال تأكيد البريد. يوصى بإضافتها لاحقًا مع مسارات العودة الآمنة واختبارها.
3. **تحقق إعدادات مطلوب:** مراجعة إعدادات Auth وSMTP والقوالب وRedirect URLs وحدود كلمات المرور والمحاولات من لوحة Supabase قبل اعتبار دورة المصادقة مكتملة.
4. **اختبار عملي مطلوب:** استخدام حساب اختبار منفصل ببريد يمكن الوصول إليه لتجربة التسجيل، تأكيد البريد، الدخول، الخروج، إعادة تعيين كلمة المرور، رابط منتهي الصلاحية، والبريد غير المؤكد. لا تستخدم حساب المالك الحالي لهذا الاختبار.
5. **ملاحظة جلسات:** وجود auto-refresh واستمرار الجلسة مقصود لتسهيل الاستخدام، لكنه لا يعوض عن تدفق استعادة كلمة المرور أو إبطال الجلسات عند الحاجة.

**حالة البند:** توثيق مراجعة الكود وسياسات Test DB فقط. لم تتغير إعدادات Auth أو الحسابات أو الجلسات أو بيانات الاختبار أو ملفات التطبيق أو قاعدة Production.

### مراجعة انتهاء الجلسة وتجديدها وانقطاع الاتصال (24 نوفمبر 2026)

تمت مراجعة preview/index.html على فرع development، مع تتبع تهيئة Supabase Auth، وتحميل مساحة العمل، وحفظ المسودات محليًا، وبعض مسارات تحميل البيانات وترحيل العمليات. لم يتم إجراء اختبار قطع اتصال فعلي أو انتهاء جلسة، ولم تُنفذ أي عملية كتابة على Test DB.

#### 1. الجلسة وتجديد التوكن

- عميل Supabase مهيأ باستخدام persistSession: true وautoRefreshToken: true وdetectSessionInUrl: true. هذا يعني أن مكتبة Supabase تتولى حفظ الجلسة ومحاولة تجديد التوكن تلقائيًا؛ لا يوجد في التطبيق منطق يدوي لاستدعاء refreshSession.
- التطبيق يستمع إلى INITIAL_SESSION وSIGNED_IN وSIGNED_OUT فقط. لا يوجد تعامل واجهي صريح مع TOKEN_REFRESHED أو USER_UPDATED أو أحداث Auth الأخرى.
- عند SIGNED_OUT يخفي التطبيق مساحة العمل ويعرض شاشة الدخول. لكن لا يوجد في هذا المعالج مسح صريح لمسودات Local Storage أو إعادة ضبط جميع متغيرات البيانات الموجودة في الذاكرة.
- لا يوجد دليل من الكود وحده على أن كل حالات فشل التجديد ستؤدي دائمًا إلى السلوك المرئي المطلوب؛ يلزم اختبار عملي بجلسة اختبار منفصلة ورصد الحدث الفعلي الذي تصدره نسخة SDK المستخدمة.

#### 2. انقطاع الإنترنت والعودة

- لم يظهر مستمع لأحداث online أو offline، ولا مستمع pageshow أو focus لإعادة فحص الجلسة أو تحديث بيانات النشاط عند عودة المستخدم للتطبيق.
- لا توجد آلية ظاهرة لإعادة تحميل تلقائية للبيانات بعد عودة الاتصال، ولا علامة اتصال حية. النص الذي يعرض «إعداد الاتصال مكتمل» يصف اكتمال الإعداد الأولي، وليس ضمانًا بأن الإنترنت أو Supabase متاحان الآن.
- بعض الشاشات تعرض رسالة تحميل ثم رسالة خطأ عند فشل الطلب. لكن في عمليات التحديث اليدوي داخل شاشة مفتوحة، لا يتم إخفاء كل البيانات السابقة بالضرورة عند فشل إعادة التحميل؛ مثال ذلك loadProducts الذي لا يستبدل قائمة المنتجات إلا بعد نجاح جلبها، فيبقى العرض السابق موجودًا إذا فشل الطلب قبل التحديث. هذا قد يجعل المستخدم يرى بيانات قديمة مع رسالة خطأ.
- في المقابل، بعض بيانات المخزون الإضافية وصور المنتجات يتم التعامل مع فشل تحميلها بتحذير في Console أو ترك بياناتها غير متاحة، وليس برسالة واضحة موحدة للمستخدم. لذلك معالجة الأخطاء ليست موحدة بين الوحدات.
- في loadWorkspace، إذا فشل auth.getUser() أو لم يُرجع مستخدمًا، يتم إظهار شاشة الدخول دون عرض سبب الاتصال للمستخدم؛ أما خطأ قراءة العضويات فيُعرض عبر رسالة الخطأ العامة.

#### 3. المسودات المحلية

- توجد آلية حفظ تلقائي في localStorage تحت المفتاح alnesr_preview_state_v1، وتعمل عند الكتابة والتغيير والنقر وإخفاء الصفحة ومغادرتها.
- المسودة تشمل قيم عدد من النماذج، وعدد بنود البيع والشراء، والقسم والتبويب المفتوحين وبعض النوافذ المفتوحة. حقول كلمة المرور والملفات وأزرار الإرسال لا تُحفظ ضمن قيم النماذج.
- الاستعادة مشروطة بتطابق معرف المستخدم ومعرف النشاط، وبألا يتجاوز عمر المسودة 7 أيام. وعند تغيير النشاط تستدعي الواجهة clearAppState.
- المسودة لا تحفظ سجلات الفواتير أو الدفعات ولا تنفذ عمليات Offline؛ هي فقط قيم نماذج وواجهة لاستكمال الإدخال بعد الرجوع.
- المسودة مخزنة في Local Storage على الجهاز وليست مشفرة بواسطة التطبيق. كما أن معالج تسجيل الخروج لا يستدعي clearAppState؛ لذلك قد تبقى بيانات النماذج على الجهاز بعد الخروج، حتى لو لم تُستعد لمستخدم مختلف بسبب شرط تطابق المستخدم والنشاط. هذه نقطة خصوصية مهمة خصوصًا على جهاز مشترك، وليست دليلًا على تجاوز صلاحيات قاعدة البيانات.

#### 4. العمليات المالية عند فشل الاتصال

- مسارات ترحيل المبيعات والمشتريات والعديد من العمليات الأخرى تستخدم RPC في قاعدة البيانات، وتعرض رسالة نجاح بعد رجوع استجابة ناجحة، وتستدعي معالج الخطأ عند رجوع خطأ.
- لم يظهر مسار Offline Queue أو إعادة إرسال تلقائية لعمليات الترحيل.
- عند انقطاع الاتصال في توقيت حساس، قد لا يعرف المستخدم من رسالة الخطأ وحدها هل وصل الطلب إلى الخادم ونُفذ ثم ضاعت الاستجابة، أم لم يصل أصلًا. لا نثبت حدوث تكرار أو فساد من الكود وحده؛ لكن قبل اعتماد سياسة إعادة المحاولة يجب اختبار انقطاع الاتصال أثناء وبعد الإرسال ومراجعة ضمانات منع التكرار في كل RPC حساسة.

#### التصنيف

1. **مؤكد من الكود:** التجديد التلقائي مفعّل داخل Supabase SDK، ولا توجد مراقبة مستقلة للاتصال أو آلية تحديث تلقائي عند عودة الإنترنت.
2. **مؤكد من الكود:** معالجة أحداث Auth في الواجهة تقتصر على INITIAL_SESSION وSIGNED_IN وSIGNED_OUT.
3. **مؤكد من الكود:** توجد مسودات محلية غير مشفرة، مرتبطة بالمستخدم والنشاط، وصلاحيتها القصوى 7 أيام، ولا تُمسح صراحة عند تسجيل الخروج.
4. **مؤكد من الكود:** بعض أخطاء إعادة التحميل قد تترك بيانات سبق عرضها ظاهرة، كما أن رسائل الأخطاء ليست موحدة بين كل الوحدات.
5. **يحتاج اختبارًا عمليًا:** انتهاء access token، فشل refresh token، انقطاع الشبكة أثناء فتح التطبيق، العودة بعد وضع التطبيق بالخلفية، وانقطاع الاتصال أثناء ترحيل فاتورة أو دفعة.
6. **يحتاج قرارًا قبل الإصلاح:** هل نمسح المسودات عند تسجيل الخروج أم نحتفظ بها لاستكمال العمل؟ وهل نعرض البيانات القديمة بعلامة واضحة أم نخفيها عند فشل التحديث؟ وما سياسة إعادة المحاولة الآمنة للعمليات المالية؟

**التوصية:** لاحقًا نضيف حالة اتصال واضحة، وتحديثًا مضبوطًا للجلسة والبيانات عند استعادة الاتصال/عودة التطبيق، ورسائل تفرق بين فشل الاتصال وفشل الصلاحية. ونراجع ضمان منع التكرار للعمليات المالية قبل تصميم أي إعادة محاولة تلقائية. لا ننفذ هذه التغييرات قبل الاتفاق والاختبار.

### مراجعة تبديل النشاط وعزل بيانات الواجهة بين الأنشطة (24 نوفمبر 2026)

تمت مراجعة تبديل النشاط في Preview على فرع development، بما يشمل معالج businessSelect، ودالة renderMembership، وloadWorkspace، ومسودات Local Storage، وعددًا من loaders. هذه مراجعة ساكنة للكود؛ لم يتم تسجيل الدخول بحسابات متعددة أو إنشاء نشاط ثانٍ أو إجراء عمليات على Test DB.

#### 1. ما يعمل بصورة صحيحة في المسار الأساسي

- قائمة الأنشطة تُبنى من عضويات المستخدم النشطة فقط عبر business_members مع active=true، ولا تعتمد على اختيار اسم نشاط من الواجهة وحده.
- كل نشاط مختار يحدد activeBusinessId، وتُبنى الصلاحيات من عضوية هذا النشاط في renderMembership.
- renderMembership يخفي وحدات الواجهة ثم يعرض أول وحدة مسموح بها، ويحدث أزرار العمليات والروابط حسب صلاحيات العضوية المختارة.
- استعلامات القراءة الأساسية التي تمت مراجعتها، مثل المنتجات والعملاء والموردين وفواتير البيع والشراء، تتضمن قيد business_id يساوي النشاط المختار. وعمليات الحفظ التي تمت مراجعتها تمرر business_id الحالي إلى قاعدة البيانات أو RPC.
- عند تغيير النشاط، تُمسح مسودة Local Storage الحالية، ويُعاد اختيار لوحة المعلومات وتحميل المنتجات ثم بيانات لوحة المعلومات. وعند تسجيل الخروج تُمسح المسودة أيضًا.

#### 2. مشكلة مؤكدة: نماذج الإدخال المفتوحة لا تُصفّر عند تبديل النشاط

- clearAppState يمسح مفتاح المسودة المحلية فقط؛ ولا يعيد ضبط عناصر النماذج في الصفحة ولا يخفي جميع لوحات التحرير الفرعية.
- renderMembership يخفي/يعرض الوحدات الرئيسية ويعيد ضبط الوحدة النشطة، لكنه لا يمسح قيم productForm أو saleForm أو purchaseForm أو بقية النماذج، ولا يغلق جميع محررات الإدخال.
- لذلك إذا كان المستخدم قد فتح نموذجًا وكتب بيانات غير محفوظة في النشاط الأول، ثم بدّل إلى نشاط آخر، فالقيم وعناصر التحرير قد تظل موجودة داخل DOM. وعند فتح الوحدة لاحقًا قد يجد النموذج القديم كما هو، بحسب حالة اللوحة الفرعية.
- هذه ليست عملية ترحيل تلقائي للبيانات؛ لكن لو حاول المستخدم حفظ النموذج بعد التبديل، بعض دوال الحفظ تستخدم activeBusinessId الحالي مع قيم النموذج القديمة. وقد ينتج عن ذلك رفض بسبب عدم تطابق المنتج/العميل/المورد مع النشاط الجديد، أو التباس للمستخدم حول النشاط الذي سيُسجل عليه الإدخال.
- نقطة القرار: هل نغلق ونصفر كل النماذج عند تبديل النشاط، أم نحفظ مسودة مستقلة لكل نشاط ثم نستعيدها فقط عند الرجوع إليه؟ لا يوجد قرار تنفيذ في هذه المراجعة.

#### 3. مشكلة مؤكدة في إدارة البيانات المعروضة: القوائم القديمة لا تُمسح قبل التحميل

- متغيرات الواجهة العامة مثل products وcustomers وsuppliers وpurchaseInvoices وsalesInvoices وpurchaseReturns تحتفظ بالبيانات في الذاكرة، ولا يظهر في معالج التبديل تصفير شامل لها.
- عدد من loaders، مثل loadCustomersModule وloadSuppliersModule وloadPurchasesModule وloadSalesModule، لا يستبدل القوائم إلا بعد نجاح طلبات القراءة. إذا فشل الطلب قبل الإسناد، تبقى القوائم السابقة في الذاكرة.
- عند فتح وحدة بعد تبديل النشاط، activateModule يجعل الوحدة ظاهرة ثم يبدأ loader. بالتالي قد تظهر نتائج النشاط السابق أثناء انتظار التحميل، وإذا فشل التحميل قد تظل النتائج السابقة معروضة مع رسالة الخطأ. هذا خطر عرض بيانات بين الأنشطة على نفس الجهاز، حتى مع بقاء عزل قاعدة البيانات وسياسات RLS.
- في loadProducts، فشل جلب المنتجات الرئيسية يترك قائمة المنتجات السابقة؛ كما أن فشل تحميل الأرشيف يعيد قبل استكمال تحديث الحالة. أما فشل تحميل رصيد المخزون أو روابط الصور فيُعامل بتحذير Console في بعض المسارات، وقد تظهر بيانات ناقصة أو قديمة دون تفسير واضح.
- هذا لا يثبت أن المستخدم يستطيع قراءة بيانات نشاط آخر من قاعدة البيانات؛ المشكلة هنا في حالة الواجهة والبيانات التي سبق تحميلها في ذاكرة المتصفح.

#### 4. احتمال تداخل التحميل عند التبديل السريع

- معالج تغيير النشاط async ويستدعي loadProducts ثم loader الوحدة. لا يوجد رقم طلب أو إلغاء للطلبات السابقة أو تحقق نهائي بأن activeBusinessId ما زال هو نفس النشاط الذي بدأ التحميل من أجله قبل إسناد النتائج إلى المتغيرات العامة.
- عدد من loaders يقرأ activeBusinessId مباشرة أثناء بناء الاستعلام، ثم يستخدم activeBusinessId مرة أخرى بعد await لتحديد الدور أو تحديث الواجهة. إذا حدث تبديل آخر قبل اكتمال الطلب الأول، قد تتداخل نتائج الطلبات في المتغيرات العامة أو تتعامل مع صلاحيات النشاط الجديد.
- هذا خطر سباق محتمل مستنتج من بنية الكود؛ يحتاج اختبارًا عمليًا بتبديل سريع بين نشاطين مع إبطاء الشبكة ومراقبة النتائج لتأكيد سيناريو إعادة الإنتاج بدقة.

#### التصنيف والتوصيات

1. **مؤكد من الكود:** عضويات النشاط النشطة هي مصدر قائمة الاختيار، والصلاحيات مرتبطة بالعضوية المختارة، والاستعلامات الأساسية التي فُحصت تقيد البيانات بـbusiness_id.
2. **مؤكد من الكود:** مسح المسودة عند التبديل لا يمسح حقول النماذج المفتوحة أو لوحات التحرير الفرعية داخل الصفحة.
3. **مؤكد من الكود:** عدة loaders تحتفظ بالقوائم السابقة عند فشل الطلب، ولا توجد عملية تصفير موحدة لكل بيانات النشاط السابق قبل إظهار الوحدة الجديدة.
4. **مؤكد من الكود:** الوحدة الجديدة تُعرض قبل اكتمال تحميلها؛ لذلك قد تبقى بيانات سابقة ظاهرة أثناء التحميل أو بعد فشله.
5. **احتمال يحتاج اختبارًا عمليًا:** تداخل طلبات نشاطين عند التبديل السريع قد يسمح لنتيجة قديمة بالكتابة فوق حالة الواجهة الأحدث.
6. **يحتاج قرارًا قبل الإصلاح:** سياسة النماذج غير المحفوظة عند التبديل، وسياسة إخفاء البيانات القديمة فورًا، وهل نستخدم حالة تحميل تمنع عرض أي قائمة حتى يكتمل تحميل النشاط الحالي.

**التوصية:** قبل السماح باستخدام عدة أنشطة فعليًا على نفس الجلسة، ينبغي أن يكون تبديل النشاط عملية انتقال ذرية للواجهة: إخفاء/تصفير بيانات النشاط السابق والنماذج، ثم تحميل بيانات النشاط الجديد، وعدم عرض النتائج إلا إذا ظل معرّف النشاط مطابقًا للطلب الذي بدأ التحميل. ويُختبر ذلك بحساب اختبار له عضويتان ونشاطان منفصلان. لم يتم تنفيذ أي إصلاح في هذه المراجعة.

**حالة البند:** توثيق مراجعة الكود فقط. لم يتم إنشاء نشاط أو عضوية جديدة، ولم تتغير أي بيانات أو صلاحيات أو إعدادات في Test DB أو Production، ولم تتغير ملفات التطبيق.

### مراجعة دورة صور المنتجات والتخزين الخاص (24 نوفمبر 2026)

تمت مراجعة دورة صور المنتجات في Preview على فرع development، مع قراءة سياسات Storage وفحص بيانات Test Supabase قراءة فقط. لم يتم رفع أو حذف أو تعديل أي ملف تخزين، ولم يتم تعديل بيانات المنتجات أو أي إعداد في قاعدة البيانات.

#### 1. الرفع وربط الصورة بالمنتج

- Bucket باسم product-images مضبوط على Private، وحد الملف 5 ميجابايت، والأنواع المسموحة JPEG وPNG وWebP.
- الواجهة تتحقق من نوع الملف وحجمه قبل الرفع، وتكرر التحقق أثناء معاينة الصورة.
- مسار الصورة الذي تنشئه الواجهة يتكون من business_id / product_id / UUID عشوائي مع امتداد مناسب. وعند إنشاء منتج جديد يُنشأ UUID للمنتج أولًا، ثم تُرفع الصورة إلى المسار، ثم يُحفظ image_path مع سجل المنتج.
- عند تعديل منتج، يتم تحديث السجل بشرط تطابق id وbusiness_id مع النشاط الحالي. وعند عدم اختيار صورة جديدة تحتفظ الواجهة بمسار الصورة القديمة، وعند اختيار إزالة الصورة تجعل image_path فارغًا.
- لا يوجد في تعريف products قيد Foreign Key أو قيد تحقق يربط image_path بكائن Storage أو يثبت أن مجلد المنتج داخل المسار تابع لنفس business_id. سلامة هذا الربط تعتمد حاليًا على كود الواجهة وسياسات التخزين.

#### 2. سياسات الوصول إلى Storage

- سياسات القراءة والرفع والتعديل والحذف مخصصة لدور authenticated، وتتحقق من صلاحية النشاط المستخرجة من أول مجلد في مسار الملف.
- القراءة تتطلب products.view، والرفع يتطلب products.create أو products.edit، والتعديل يتطلب products.edit، والحذف يتطلب products.edit أو ملكية الملف مع products.create.
- سياسة الرفع تشترط وجود جزء ثانٍ في المسار، لكنها لا تتحقق أن هذا الجزء هو UUID لمنتج موجود، ولا أن المنتج يتبع النشاط الموجود في الجزء الأول. لذلك يمكن نظريًا إنشاء كائن تخزين داخل مجلد نشاط مصرح به مع معرّف منتج غير موجود أو غير تابع له؛ وهذا قد ينتج ملفات يتيمة أو ربطًا غير متسق، وليس دليلًا على إمكانية قراءة بيانات نشاط آخر.
- لا توجد سياسة قراءة عامة؛ والـBucket خاص. لم يظهر في المسارات التي تمت مراجعتها استخدام رابط عام للصورة.

#### 3. عرض الصور وتجديد الروابط

- عند تحميل المنتجات، تطلب الواجهة روابط Signed URLs لمدة 3600 ثانية (ساعة) للصور الموجودة في القائمة الحالية.
- إذا فشل إنشاء الروابط، تسجل الواجهة تحذيرًا في Console وتكمل عرض المنتجات؛ لا يظهر مسار واضح لإعادة محاولة إنشاء الروابط فورًا أو رسالة مخصصة للمستخدم.
- الرابط المؤقت الذي تم إنشاؤه لا يُجدد تلقائيًا أثناء بقاء الصفحة مفتوحة بعد انتهاء الساعة؛ التجديد مرتبط بإعادة تحميل المنتجات/المسار الذي ينشئ الروابط. لذلك قد تتوقف صورة عن الظهور في صفحة ظلت مفتوحة مدة طويلة حتى يتم تحميل المنتجات مرة أخرى.
- فشل تحميل رابط صورة لا يوقف تحميل قائمة المنتجات كلها؛ لكنه قد يترك الصورة دون رابط عرض صالح.

#### 4. استبدال الصورة وإزالتها وحذف المنتج

- عند استبدال الصورة، ترفع الواجهة الصورة الجديدة أولًا إلى مسار UUID جديد، ثم تحفظ image_path الجديد في سجل المنتج. إذا فشل حفظ سجل المنتج تحاول حذف الملف الجديد الذي رفعته، لتجنب ترك ملف غير مرتبط.
- بعد نجاح حفظ الصورة الجديدة، تحذف الواجهة الصورة القديمة بشكل غير متزامن. إذا فشل حذفها تسجل تحذيرًا في Console فقط؛ وقد يبقى الملف القديم في Storage دون مرجع من المنتج.
- عند إزالة الصورة من نموذج المنتج، يُحفظ image_path فارغًا ثم تحاول الواجهة حذف الملف القديم بصورة غير متزامنة، مع نفس احتمال بقاء ملف يتيم عند فشل الحذف.
- عند حذف منتج نهائيًا عبر owner_remove_product، تحاول الواجهة حذف صورته بعد نجاح RPC. أما إذا تمت أرشفة المنتج بسبب وجود سجلات مرتبطة به، فلا تحذف الصورة، وهذا متسق مع بقاء سجل المنتج وإمكانية استعادته.
- نتيجة حذف كائن Storage بعد حذف المنتج لا يتم فحصها لإظهار فشل واضح للمستخدم في هذا المسار؛ لذلك قد ينجح حذف سجل المنتج وتبقى صورته في التخزين إذا فشل طلب الحذف.

#### 5. النسخ الاحتياطي والاستعادة

- تصدير النسخة ينشئ Signed URLs للصور ثم ينزل محتواها ويتحقق من نوع الملف وحجمه قبل تضمينها.
- أثناء الاستعادة تتحقق الواجهة من أن كل صورة في النسخة مرتبطة بمسار صورة منتج داخل النشاط الحالي، وأن شكل المسار ومعرفات UUID والامتداد ونوع المحتوى والحجم متوافقة.
- ترفع الواجهة الصور إلى Storage أولًا، ثم تستدعي RPC استعادة البيانات. وإذا فشلت عملية الاستعادة تحاول حذف الصور التي رفعتها في هذه المحاولة.
- إذا فشل تنظيف الصور بعد فشل الاستعادة، تظهر رسالة تحذر من بقاء ملفات مؤقتة وتطلب عدم تكرار المحاولة دون مراجعة. لم يتم تنفيذ استعادة فعلية أثناء هذه المراجعة.

#### 6. فحص بيانات Test Storage الحالية

- في لحظة الفحص كان Bucket يحتوي على كائن واحد فقط.
- جدول المنتجات في Test DB كان يحتوي على 3 سجلات، ولا يوجد أي سجل منها يحمل image_path.
- كائن Storage الموجود لا يشير إلى image_path لأي منتج، كما أن معرّف مجلد المنتج في مساره لا يطابق منتجًا موجودًا. هذا كائن غير مرتبط حاليًا بمنتج؛ لا يمكن تحديد سبب بقائه من القراءة وحدها، ولذلك لم يتم حذفه أو تغييره.
- هذه لقطة لحالة Test DB وقت الفحص فقط، ولا تعني أن كل صور Production أو تاريخ التخزين قد تمت مراجعته.

#### التصنيف والتوصيات

1. **مؤكد من الكود والإعدادات:** Bucket خاص، وحده 5 ميجابايت، والأنواع المسموحة JPEG وPNG وWebP، والواجهة تستخدم مسارًا يتضمن النشاط والمنتج ومعرفًا عشوائيًا.
2. **مؤكد من الكود:** استبدال الصورة يتم برفع الجديد ثم تحديث سجل المنتج ثم محاولة حذف القديم؛ وفشل حذف القديم قد يترك كائنًا يتيمًا.
3. **مؤكد من الكود:** روابط الصور المؤقتة مدتها ساعة، ولا يوجد تجديد تلقائي مستقل أثناء بقاء الصفحة مفتوحة.
4. **مؤكد من السياسات:** سياسات Storage تتحقق من صلاحية النشاط في أول مجلد، لكن لا تتحقق من وجود المنتج في المجلد الثاني أو انتمائه إلى النشاط نفسه.

6. **يحتاج اختبارًا عمليًا:** تجربة فشل رفع الصورة، وفشل حفظ المنتج بعد الرفع، وفشل حذف الصورة القديمة، وانتهاء Signed URL أثناء بقاء الصفحة مفتوحة، مع التحقق من عدم ظهور صور نشاط في نشاط آخر.
7. **يحتاج قرارًا قبل الإصلاح:** هل نضيف تحققًا مرجعيًا صارمًا بين مسار الصورة والمنتج والنشاط؟ وهل نضيف آلية دورية لمراجعة الملفات اليتيمة وتنظيفها بعد تأكيد عدم استخدامها؟ لا ينبغي حذف الملفات تلقائيًا قبل وجود تقرير ومراجعة آمنة.

**التوصية:** تحسين التحقق من أن المنتج الموجود في المجلد الثاني تابع للنشاط نفسه، وإضافة معالجة واضحة لفشل حذف الصور وتجديد الروابط المؤقتة. كما يُفضّل توفير تقرير للملفات اليتيمة قبل أي تنظيف، مع إبقاء الحذف اليدوي خاضعًا لموافقة صريحة. لم يتم تنفيذ أي إصلاح أو حذف في هذه المراجعة.

### مراجعة اكتمال النسخ الاحتياطي والاستعادة وتصفير بيانات النشاط (24 نوفمبر 2026)

تمت مراجعة قائمة الجداول التي تصدرها الواجهة، ودالة restore_business_backup، ودالة reset_business_data الفعلية في Test Supabase، مع مراجعة العلاقات المرجعية للجداول المضافة حديثًا. كل استعلامات قاعدة البيانات كانت للقراءة فقط؛ لم يتم تشغيل النسخ أو الاستعادة أو التصفير فعليًا.

#### 1. ما الذي يدخل في ملف النسخة حاليًا؟

- ملف النسخة بصيغة alnesr-business-backup-v2، ويُنشأ لمالك النشاط فقط.
- قائمة التصدير الحالية تحتوي على: products, parties, purchase_invoices, purchase_items, purchase_invoice_cost_snapshots, sales_invoices, sales_items, payments, stock_movements, stock_adjustment_cost_snapshots, sales_returns, sales_return_items, expenses, cash_transactions, business_settings, audit_log.
- يتم جلب كل جدول بطلبات منفصلة مع تقسيم الصفحات إلى دفعات من 1000 سجل، ثم تُضمّن صور المنتجات بعد تنزيلها من Storage الخاص.
- حد الملف النهائي 100 ميجابايت، وحد الصورة 5 ميجابايت. أي فشل في قراءة جدول أو صورة يوقف التصدير بدل إنتاج نسخة معلنة على أنها مكتملة.
- لأن الجداول تُقرأ في طلبات منفصلة، لا يوجد Snapshot واحد مشترك يضمن أن كل الجداول تمثل اللحظة نفسها إذا كانت هناك عمليات بيع أو شراء أو دفعات تحدث بالتزامن مع التصدير. هذا احتمال عدم اتساق يحتاج اختبارًا وتصميمًا، وليس دليلًا على أن ملفًا حاليًا تالف.

#### 2. جداول موجودة في قاعدة البيانات لكنها غير مشمولة في النسخة

الجداول التالية موجودة في Test DB، لكنها غير موجودة في قائمة التصدير، ولا في قائمة الجداول التي تستوردها restore_business_backup:

- purchase_returns وpurchase_return_items: مرتجعات المشتريات وبنودها.
- customer_credit_ledger: سجل حركة رصيد العميل الدائن.
- treasury_transfers: سجل التحويلات بين وسائل/أرصدة الخزنة.
- operation_counters: عدادات أرقام العمليات.

وبالتالي، حتى لو نجح تصدير واستعادة بقية البيانات، فلن تعود هذه السجلات من ملف النسخة الحالي. هذا نقص مؤكد في اكتمال النسخة الحالية.

- business_members غير مشمول أيضًا. استبعاده قد يكون مقصودًا لحماية عضويات وصلاحيات الوصول وعدم نقلها تلقائيًا مع البيانات؛ ينبغي توثيق هذا القرار صراحة وعدم استعادة العضويات كجزء من نسخة البيانات دون تصميم أمني واضح.

#### 3. ما الذي تتحقق منه الاستعادة؟

- الواجهة تشترط الإصدار v2 وأن يكون business_id في الملف مطابقًا للنشاط الحالي، وتتحقق من وجود مصفوفات الجداول الأساسية، وتتحقق من صور المنتجات ومساراتها ومحتواها.
- دالة restore_business_backup تتحقق من هوية المالك والنشاط وصيغة الملف، وتستخدم قفلًا خاصًا بالنشاط، وتمنع الاستعادة فوق سجلات موجودة في الجداول الموجودة بقائمة required_tables.
- الدالة تتحقق من عدد من العلاقات المهمة، ومنها لقطات تكاليف المشتريات وتسويات المخزون، وربط الدفعات بالفواتير، وحركات الخزنة بالدفعات والفواتير، والمصروفات بحركات الخزنة، ومسارات صور المنتجات.
- الإدخال يتم داخل RPC واحدة، وترتيب إدخال الجداول يراعي عددًا من العلاقات، مع إدخال قيود العكس بعد القيود الأصلية. أخطاء قاعدة البيانات داخل العملية تؤدي إلى فشل المعاملة بدل اعتماد جزء من البيانات فقط.
- لكن قائمة required_tables نفسها لا تشمل جداول مرتجعات المشتريات أو سجل رصيد العميل أو تحويلات الخزنة أو العدادات؛ لذلك لا تُلزم الاستعادة بوجود بياناتها في الملف، ولا تستوردها، ولا تفحص خلو بعضها قبل الاستعادة.

#### 4. مشكلة مؤكدة في دالة تصفير النشاط

- reset_business_data تحذف عددًا من الجداول الأساسية، لكنها لا تحذف purchase_returns أو purchase_return_items أو customer_credit_ledger أو treasury_transfers أو operation_counters.
- في Test DB وقت الفحص وُجدت سجلات فعلية في الجداول المهملة: مرتجعا مشتريات وبنداهما، وسجلان في customer_credit_ledger، و12 تحويل خزنة، و9 صفوف عدادات.
- العلاقات المرجعية الفعلية تجعل هذا النقص مؤثرًا: purchase_returns تشير إلى فواتير مشتريات، وبنودها تشير إلى purchase_items والمنتجات؛ وcustomer_credit_ledger يشير إلى العملاء وفواتير البيع، وقد يشير إلى مرتجعات أو دفعات. بعض هذه العلاقات تستخدم RESTRICT أو NO ACTION.
- في البيانات الحالية وُجدت مرتجعات مشتريات مرتبطة بفواتيرها وبنودها، كما وُجد سجل رصيد عميل مرتبط بفاتورة بيع. ودالة التصفير تحاول حذف السجلات الأصلية دون حذف هذه السجلات التابعة أولًا.
- لذلك يُتوقع أن يفشل reset_business_data حاليًا عند الوصول إلى حذف سجل أبٍ تشير إليه هذه الجداول، وتُلغى المعاملة بدل تصفير جزئي. هذا استنتاج مؤكد من ترتيب الحذف والقيود والبيانات الموجودة، لكن لم نشغّل الدالة لإثبات رسالة الخطأ عمليًا، ولم نحاول التصفير.
- treasury_transfers وoperation_counters لا يظهر أنهما يُصفّران في هذه الدالة. بقاء العدادات قد يكون مقصودًا لمنع إعادة استخدام أرقام العمليات؛ أما بقاء سجل التحويلات بعد حذف حركات الخزنة فيحتاج قرارًا واضحًا حول معنى التصفير وما الذي يجب الاحتفاظ به.

#### 5. مخاطر إضافية تحتاج اختبارًا أو قرارًا

- التصدير المتتابع للجداول قد ينتج لقطة غير متزامنة إذا تغيرت البيانات أثناء التصدير. الأفضل لاحقًا اعتماد آلية تصدير متسقة زمنيًا أو منع العمليات أثناء أخذ النسخة، مع توضيح أثر ذلك.
- الواجهة ترفع صور النسخة إلى Storage قبل استدعاء RPC الاستعادة، وتحاول حذف الصور المرفوعة إذا رجعت RPC بخطأ. إذا انقطع الاتصال في لحظة غامضة بعد تنفيذ الاستعادة وقبل وصول الاستجابة، يجب اختبار هل يمكن أن تعتبر الواجهة العملية فاشلة وتحذف صورًا أصبحت البيانات المستعادة تشير إليها. هذا سيناريو محتمل يحتاج اختبارًا مضبوطًا، ولم يحدث في هذه المراجعة.
- يجب أن تغطي اختبارات الاستعادة كل العلاقات التابعة، بما فيها مرتجعات المشتريات ورصيد العميل والتحويلات، وأن تقارن أعداد السجلات والأرصدة وأرقام العمليات قبل وبعد الاستعادة.
- يجب اتخاذ قرار مستقل بشأن عدادات العمليات: هل تُستعاد كما كانت في النسخة، أم يُحتفظ بالعداد الحالي، أم تُعاد تهيئتها بطريقة تمنع تكرار أرقام سبق إصدارها؟ لا ينبغي اختيار سلوك تلقائي قبل الاتفاق.

#### التصنيف والتوصية

1. **مؤكد من الكود وقاعدة Test:** قائمة التصدير والاستعادة لا تشمل مرتجعات المشتريات وبنودها، أو سجل رصيد العميل، أو تحويلات الخزنة، أو عدادات العمليات.
2. **مؤكد من الكود والعلاقات والبيانات الحالية:** دالة reset_business_data لا تحذف بعض السجلات التابعة، ويوجد في Test DB ما يرتبط بفواتير وبنود ستُحذف؛ لذلك يُتوقع فشل التصفير بسبب قيود العلاقات. لم يتم تشغيل الدالة.
3. **مؤكد من الكود:** الاستعادة تمنع الكتابة فوق بيانات موجودة في الجداول المحددة فقط، وتتحقق من عدد من العلاقات المرجعية، لكنها لا تستورد الجداول الجديدة غير المدرجة.
4. **قرار مقصود مطلوب:** هل business_members مستبعد عمدًا من النسخة؟ وما سياسة operation_counters عند التصفير والاستعادة؟
5. **يحتاج اختبارًا عمليًا:** أخذ نسخة أثناء عمليات متزامنة، واستعادة نسخة على نشاط فارغ، ومحاكاة انقطاع الاستجابة بعد رفع الصور/تنفيذ RPC، والتحقق من جميع الأرصدة والعلاقات.
6. **التوصية:** لا تستخدم حاليًا خيار تصفير البيانات أو تعتبر النسخة الحالية نسخة كاملة لكل بيانات النشاط قبل إصلاح النقص ومناقشة سياسة العضويات والعدادات. يجب أولًا تصميم ترتيب حذف واستعادة يشمل الجداول التابعة، ثم اختبار ذلك على بيئة اختبار منفصلة قابلة للإرجاع، دون المساس ببيانات Production.

**حالة البند:** مراجعة ساكنة للكود وقراءة تعريفات قاعدة Test وبياناتها فقط. لم يتم تنزيل نسخة فعلية أو استعادتها أو تصفير أي نشاط، ولم يتم تغيير أي سجل أو ملف أو سياسة في Test DB أو Production، ولم يتم تعديل التطبيق.

## مراجعة ترقيم العمليات والعدادات (24 نوفمبر 2026)

### 1. طريقة تكوين الرقم

- دالة `next_operation_code(business_id, operation_type)` في Test DB تولّد الكود من تاريخ القاهرة بصيغة `DDMMYY` ثم رقم تسلسلي متزايد.
- التسلسل مستقل لكل نوع عملية داخل النشاط، وليس تسلسلًا واحدًا مشتركًا لكل أنواع العمليات، ولا يبدأ من جديد كل يوم.
- أمثلة من السجلات الحالية: أكواد فواتير ومرتجعات تبدأ بتاريخ اليوم ثم رقم التسلسل، بينما أكواد أقدم تحمل تاريخ اليوم الذي أُنشئت فيه.
- إنشاء فواتير البيع والشراء ومرتجعاتهما يستدعي الدالة من داخل RPC الترحيل. أما الأطراف والدفعات وحركات الخزنة والمصروفات والتحويلات وحركات المخزون، فلها Triggers قبل INSERT تستدعي `assign_business_record_code` ثم `next_operation_code` إذا كان حقل الكود فارغًا.
- واجهة Preview لا تعتمد على حساب الرقم محليًا: فاتورة الشراء/البيع ترسل البيانات إلى RPC، ومرتجع المشتريات يرسل `AUTO`، بينما مرتجع المبيعات يرسل القيمة المدخلة. الكود النهائي يُولّد داخل قاعدة البيانات في مسارات الترحيل التي تمت مراجعتها.

### 2. الحماية من التزامن وتكرار الأرقام

- الدالة تأخذ `pg_advisory_xact_lock` خاصًا بالنشاط ونوع العملية، ثم تقرأ صف العداد `FOR UPDATE` وتزيد `last_number`. هذا يمنع عمليتين متزامنتين تستخدمان الدالة لنفس النشاط والنوع من تخصيص الرقم نفسه.
- تحديث العداد وإدخال السجل يحدثان ضمن معاملة قاعدة البيانات نفسها عند استدعاء RPC/Trigger؛ إذا فشلت العملية ورجعت المعاملة، يرجع تحديث العداد معها. لم ننفذ اختبار تزامن عمليًا، لذلك سلوك السباق مؤكد من تصميم القفل لا من اختبار ضغط فعلي.
- `next_operation_code` و`assign_business_record_code` معرفتان كـSECURITY DEFINER، مع `search_path` مضبوط فارغًا في إعداد الدالتين، وتتحقق دالة الترقيم من وجود مستخدم مسجل وعضوية نشطة في النشاط.
- الدالة الداخلية غير ممنوحة مباشرة لـanon أو authenticated في Test DB؛ استخدامها يأتي من مسارات قاعدة البيانات المصرح بها. جدول `operation_counters` عليه RLS، ولا يملك authenticated صلاحيات INSERT/UPDATE/DELETE مباشرة، ولا يملك anon صلاحية SELECT.
- توجد قيود/فهارس فريدة على كود النشاط في الفواتير والمرتجعات، الأطراف، الدفعات، حركات الخزنة، المصروفات، التحويلات، وحركات المخزون. هذه القيود طبقة حماية إضافية من تكرار الكود حتى لو حدث خلل في مسار التوليد.

### 4. نقطة الخطر المرتبطة بالنسخ والاستعادة

- إذا لم يوجد صف عداد لنوع عملية، فالدالة الحالية تستخدم `COUNT(*) + 1` من الجدول المقابل لإنشاء أول قيمة. هذا ليس ضمانًا كافيًا إذا كانت هناك سجلات قديمة أكوادها أعلى من عدد السجلات الحالي، مثل حالة الحذف أو الاستعادة الجزئية؛ قد يحاول النظام إصدار كود مستخدم سابقًا.
- القيد الفريد سيمنع اعتماد سجل مكرر، لكنه قد يحوّل الحالة إلى فشل في العملية بدل معالجة العداد تلقائيًا.
- ملف النسخ الاحتياطي الحالي لا يصدر ولا يستعيد `operation_counters`. كما أن استعادة البيانات تشترط نشاطًا مطابقًا. إذا تمت الاستعادة في نشاط لا يحتوي على عدادات محفوظة، فمسار التهيئة بالعدد قد لا يعكس أعلى تسلسل سبق إصداره.
- في المقابل، عدم حذف العدادات عند تصفير البيانات يحافظ على استمرار التسلسل ويقلل خطر إعادة استخدام رقم سبق إصداره. لكنه يعني أن الأرقام قد تقفز بعد التصفير، وهذا سلوك منطقي إذا كان المطلوب عدم تكرار أرقام المستندات.
- يلزم اتخاذ قرار صريح: هل يجب أن تتضمن النسخة العدادات؟ وكيف تتم إعادة بنائها عند الاستعادة؟ التوصية الفنية هي ألا تُعاد العدادات إلى عدد السجلات، بل تُضبط إلى قيمة لا تقل عن أعلى تسلسل سبق إصداره لكل نوع، مع الاحتفاظ بتاريخ الإصدار أو ضمان عدم إعادة استخدام الأكواد القديمة.

### 5. التصنيف والنتيجة

1. **مؤكد من الكود:** الترقيم متسلسل لكل نوع داخل النشاط، وبادئة التاريخ يومية، مع قفل advisory وقفل صف العداد.
2. **مؤكد من Test DB:** RLS مفعّل على جدول العدادات، ولا توجد صلاحيات كتابة مباشرة لـauthenticated أو قراءة لـanon، والعدادات الحالية مسجلة بالقيم أعلاه.
3. **مؤكد من القيود:** توجد حماية فريدة لأكواد المستندات والعمليات الأساسية على مستوى النشاط.
4. **نقطة تحتاج معالجة تصميمية:** مسار إنشاء العداد عند غيابه يعتمد على عدد السجلات لا أعلى تسلسل سابق؛ وقد لا يكون آمنًا بعد استعادة ناقصة أو حذف تاريخي.
5. **قرار مطلوب:** هل نضيف `operation_counters` إلى النسخة والاستعادة؟ وما السياسة المطلوبة عند تصفير النشاط: استمرار التسلسل أم إعادة الترقيم؟ التوصية هي استمرار التسلسل وعدم إعادة استخدام أرقام سابقة.
6. **يحتاج اختبارًا عمليًا:** عمليتان متزامنتان من نفس النوع، فشل عملية بعد حجز الرقم، استعادة بيانات دون عدادات، وحالة حذف سجلات مع بقاء أكوادها السابقة.

**حالة البند:** مراجعة ساكنة للكود وقراءة Test DB فقط. لم يتم إنشاء فواتير أو مرتجعات أو دفعات أو تحويلات، ولم يتم تعديل بيانات Test أو Production أو التطبيق.

## مراجعة الأرصدة المالية وحركة وسائل الدفع (24 نوفمبر 2026)

### 1. طريقة احتساب حساب العميل والمورد

- View `party_account_balances` يحسب رصيد العميل من: الرصيد الافتتاحي المستحق لنا + فواتير البيع غير الملغاة - التحصيلات المرتبطة بفواتير البيع أو التحصيلات المستقلة - مرتجعات المبيعات + المبالغ التي رُدّت نقدًا للعميل.

- رصيد النقدية الحالي حسب View `cash_balances`: 195.
- حركات جدول `cash_transactions` الموجودة حاليًا كلها على `account_method='cash'`. لا توجد في البيانات الحالية حركات إيداع/سحب يدوي مسجلة على وسائل غير نقدية.

### 4. مشكلة مؤكدة في حساب الرصيد داخل بعض RPCs

- View `cash_balances` يحسب النقدية فقط من الصفوف التي يكون فيها `account_method='cash'`.
- لكن `record_invoice_payment` و`record_standalone_party_payment`، عند تسجيل سداد مورد نقدًا، يجمعان كل صفوف `cash_transactions` للنشاط دون شرط `account_method='cash'`. إذا وُجد إيداع أو سحب يدوي على إنستاباي أو البنك أو المحفظة، سيدخل في حساب النقدية رغم أنه ليس نقدًا؛ وهذا قد يسمح بصرف نقدية أكبر من رصيدها الفعلي.
- في الدالتين نفسيهما، عند اختيار وسيلة غير نقدية، يتم حساب الرصيد من الدفعات والتحويلات فقط، ولا تُضاف الإيداعات/السحوبات اليدوية المسجلة في `cash_transactions` لتلك الوسيلة. قد يؤدي ذلك إلى رفض عملية سليمة بسبب عدم ظهور رصيد يدوي متاح.
- الواجهة الحالية تستخدم هاتين الدالتين فعلًا عند تسجيل دفعات الفواتير والدفعات المستقلة. لذلك هذه ليست مجرد دوال قديمة غير مستخدمة.
- دوال أحدث مثل `record_treasury_withdrawal` و`post_purchase_with_method` ونسخة الثمانية معاملات من `post_sales_return` تستخدم View النقدية للنقد أو تضيف الحركات اليدوية مع قيد وسيلة الحساب في المسارات غير النقدية؛ أي إن منطق حساب الرصيد غير موحّد بين كل عمليات الصرف.

### 5. مسارات قديمة ما زالت قابلة للاستدعاء

- ما زالت نسخة `post_sales_return` ذات السبعة معاملات موجودة كـSECURITY DEFINER وقابلة للتنفيذ من authenticated، بجانب نسخة الثمانية معاملات التي تستخدمها الواجهة الحالية.
- كذلك توجد دالة `post_purchase` القديمة ودالة `record_cash_withdrawal` القديمة، وكلها ما زالت قابلة للتنفيذ من authenticated. لم تظهر استدعاءات لها في مسارات الواجهة الحالية التي تمت مراجعتها.
- بعض هذه المسارات القديمة تتحقق من رصيد النقدية بجمع كل `cash_transactions` دون تقييد `account_method='cash'`. كما أن نسخة مرتجع المبيعات القديمة لا تستخدم نفس سجل رصيد العميل الدائن الحديث، وقد سبق توثيق اختلاف منطقها.
- وجودها لا يثبت أن مستخدمًا استدعاها، لكنه يترك مسارات مالية قديمة متاحة عبر RPC. يلزم قرار ومراجعة مستقلة قبل تعطيلها أو تحويلها إلى wrappers، ولا يتم ذلك ضمن هذا التدقيق.

### 6. التصنيف والتوصية

1. **مؤكد من الكود:** يوجد اختلاف في احتساب أرصدة وسائل الدفع داخل `record_invoice_payment` و`record_standalone_party_payment`: النقدية لا تُفلتر حسب وسيلة الحساب، والوسائل غير النقدية لا تحتسب الإيداعات/السحوبات اليدوية.
2. **مؤكد من البيانات الحالية:** أرصدة العملاء والموردين متطابقة حاليًا، ورصيد العميل الدائن صفر، ورصيد النقدية 195، ولم تظهر دفعات نقدية غير مرتبطة أو فروق في المبالغ والاتجاهات بين الدفعات وحركات الخزنة.
3. **لا يوجد دليل حالي على فساد مالي بسبب المشكلة:** لا توجد حاليًا حركات يدوية على وسائل غير نقدية داخل `cash_transactions`، لذلك لم يظهر أثر فعلي للمشكلة في بيانات Test الحالية.
4. **مسارات قديمة تحتاج قرارًا:** توجد RPCs مالية قديمة ما زالت قابلة للاستدعاء من authenticated رغم عدم ظهور استخدامها في الواجهة الحالية.
5. **اختبارات لازمة قبل أي إصلاح:** إيداع غير نقدي يدوي ثم محاولة دفع مورد من الوسيلة نفسها، وإجراء سداد نقدي مع وجود رصيد كبير في وسيلة غير نقدية، واختبار عكس دفعة/مرتجع، ومقارنة كل الأرصدة قبل وبعد.
6. **التوصية:** توحيد مصدر حساب الرصيد في جميع RPCs إلى قاعدة واحدة: النقدية من `cash_balances`، وكل وسيلة غير نقدية من الدفعات + التحويلات + الحركات اليدوية الخاصة بنفس `account_method` فقط، مع استبعاد القيود المرتبطة التي تم احتسابها في مصدر آخر منعًا للتكرار. ثم مراجعة المسارات القديمة واتخاذ قرار بشأنها.

**حالة البند:** مراجعة ساكنة للكود وقراءة Test DB فقط. لم يتم تسجيل دفعات أو مرتجعات أو إيداعات أو سحوبات أو تحويلات تجريبية، ولم يتم تعديل أي بيانات أو دوال أو ملفات تطبيق أو إعدادات في Test أو Production.
