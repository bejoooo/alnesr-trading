## الهدف والحدود

نقل واجهة Preview الحالية لتصبح الواجهة الأساسية دون فقد بيانات النشاط أو العضوية أو تغيير التصميم/السلوك المعتمد.

- الخطة يجب أن تبقى مجانية؛ لا Supabase Branch مدفوع، ولا مشروع جديد مدفوع.
- لا تعديل على Production أو `main` قبل موافقة صريحة على خطة التنفيذ المحددة.
- لا إعادة تشغيل ملفات SQL القديمة بالتتابع.
- لا نقل بيانات الاختبار إلى Production.
- لا حذف `app/` القديمة؛ تبقى نسخة رجوع حتى يثبت نجاح النشر.
- لا تنفيذ عمليات مالية حقيقية كاختبار.

## خطة التنفيذ المرحلية

### المرحلة 0 — حماية خط الأساس
الحالة: مراجعة قراءة فقط تمت جزئيًا؛ لم يتم إنشاء نسخة احتياطية مستقلة قابلة للاستعادة.

قبل أي DDL على Production:
1. توثيق تعريفات الجداول والأعمدة والقيود والفهارس وRLS وACL والـViews والدوال والـTriggers الحالية.
2. تصدير بيانات النشاط والعضوية وكل البيانات الموجودة بطريقة متاحة مجانًا، والتحقق من إمكانية قراءتها/استعادتها في Test دون الكتابة فوق Test الحالية.
3. حفظ نسخة من نقطة الدخول الحالية وملفات الواجهة وإعدادات النشر.
4. تسجيل counts قبل الترقية لاستخدامها في المقارنة بعد الترقية.

لا تبدأ المرحلة التالية إذا لم تتوفر نسخة احتياطية قابلة للتحقق.

### المرحلة 1 — أعمدة ومفاتيح أم additive
إضافة الأعمدة الناقصة فقط بعد التحقق من عدم وجودها، مع أنواعها وقيودها الافتراضية المتوافقة مع البيانات الحالية. تجهيز المفاتيح الفريدة المركبة المطلوبة قبل إنشاء علاقات same-business.

لا تستخدم DROP/RENAME أو تحويل نوع قد يفقد بيانات. أي backfill يجب أن يكون محدودًا وقابلًا لإعادة التشغيل.

### المرحلة 2 — الجداول السبعة الجديدة
إنشاء الجداول السبعة وفق تعريفات Test، مع:
- مفاتيح أساسية وفريدة وقيود تحقق.
- علاقات مركبة تمنع ربط سجلات من نشاط مختلف.
- فهارس للمفاتيح الخارجية والاستعلامات التشغيلية.
- RLS مفعّل من لحظة الإنشاء.
- أقل صلاحيات مباشرة ممكنة؛ لا GRANT إلى anon أو PUBLIC.
- `operation_counters` لا تمنح صلاحيات كتابة مباشرة للأدوار؛ الوصول عبر RPC مخصص.

لا تنقل صفوف Test. تهيئة العدادات تكون من بيانات Production بعد تحليل الأكواد الموجودة.

### المرحلة 3 — Triggers والترقيم
إضافة Triggers الأكواد بعد فحص الأكواد الموجودة في Production، وتحديد أعلى لاحقة فعلية لكل نوع ونشاط. يجب إصلاح تهيئة العداد بحيث لا تعتمد على COUNT(*) فقط إذا كانت هناك فجوات أو حذف أو إدخال يدوي. اختبار التزامن في Test قبل اعتمادها.

### المرحلة 4 — Views
إعادة بناء Views لتطابق دلالات Preview، مع الحفاظ على `security_invoker=true`:
- `cash_balances`: النقدية فقط في حساب cash، وعدم دمج وسائل الدفع الأخرى.
- `product_stock_balances`: فصل sellable وdamaged.
- `party_account_balances` و`party_account_statement`: صافي مرتجعات المورد، الدفعات المستقلة والعكس، التوقيت الفعلي.
- Views دفتر الرصيد الدائن للعميل.

### المرحلة 5 — RPCs التشغيلية حسب الاعتماديات
ترتيب البناء المقترح:
1. دوال العضوية والصلاحيات المساعدة بعد مراجعة auth.uid والعضوية النشطة.
2. دوال المنتجات والأطراف والأرصدة الافتتاحية.
3. الشراء والبيع وحساب التكلفة وحركات المخزون.
4. الدفعات المستقلة ودفعات الفواتير وربطها بحركات الخزنة.
5. مرتجعات المبيعات والشراء، الرصيد الدائن للعميل والمورد.
6. التحويلات بين وسائل الدفع والإيداع والسحب والمصروفات.
7. العكس والإلغاء بعد وجود كل الجداول والروابط والـViews.
8. backup/restore في مسار منفصل وبعد اختبارات توافق مخصصة.

كل دالة تشغيلية حساسة يجب أن تراجع: المالك، SECURITY DEFINER، search_path فارغ/آمن، التحقق من auth.uid والعضوية والصلاحية، قفل الصفوف، منع العكس المكرر، وACL authenticated فقط حيث يلزم. لا EXECUTE لـanon أو PUBLIC.

### المرحلة 6 — نقاط لا بد من حسمها قبل كتابة الحزمة النهائية
- متوسط تكلفة المخزون: هل يشمل كل الكمية الفعلية أم الكمية الصالحة للبيع فقط؟ لا يتم اختيار أحدهما بالافتراض.
- إعادة بناء منطق 055/056 من تعريفات Test الحالية ومراجعة الأثر؛ لا اختلاق المصدر الأصلي.
- اعتماد مفاتيح مركبة same-business للجداول التي تفتقدها حاليًا.
- استراتيجية الأكواد والعدادات عند وجود أكواد قديمة أو فجوات.
- مراجعة صلاحية قراءة الدفعات المستقلة للموظفين وفق `payments.view` وصلاحيات الحساب.
- مراجعة سلوك المرتجعات متعددة الفواتير كمطلب مستقبلي غير منفذ؛ لا يدخل في هذه الترقية ولا يُدّعى أنه مدعوم.

### المرحلة 7 — تحقق قاعدة البيانات
قبل اعتماد Production:
- مقارنة counts وschema قبل/بعد.
- التحقق من وجود كل جدول وعمود وقيد وفهرس وView وTrigger وRPC مطلوب.
- فحص RLS وACL وSECURITY DEFINER وsearch_path.
- تشغيل اختبارات قراءة وتدفقات غير مالية على Test.
- استخدام حسابات بأدوار مختلفة للتحقق من الصلاحيات.
- اختبار حالات العكس المكرر، الترتيب الزمني، الرصيد غير الكافي، النشاط غير النشط، وربط النشاط.
- لا تنفذ حركات مالية حقيقية على Production بغرض الاختبار.
- لا تدّعِ اختبارًا حيًا إذا كان المنفذ مجرد مراجعة ساكنة.

### المرحلة 8 — تجهيز الواجهة والتحويل
- إبقاء `preview/index.html` على مشروع Test كما هو.
- إنشاء نسخة إنتاج مستقلة من نفس الواجهة، مرتبطة بمشروع Production بعد اكتمال قاعدة البيانات.
- لا تستخدم service-role key في المتصفح.
- إبقاء `app/` القديمة كنسخة رجوع.
- تحديث `index.html` و`manifest.json` معًا حتى لا يظل PWA يفتح `./app/`.
- تأكيد مصدر GitHub Pages والفرع/المجلد قبل النشر.
- بعد النشر، تحقق من الرابط المباشر، تسجيل الدخول، التثبيت، تحديث التطبيق المثبت، والعودة إلى النسخة السابقة إذا ظهر خلل.

## بوابات الموافقة

1. هذه الوثيقة خطة ومراجعة فقط؛ لا تنفذ DDL/DML.
2. أي Migration على Production يتطلب عرض الحزمة النهائية ومخاطرها وطلب موافقة صريحة قبل التنفيذ.
3. تغيير `main` أو نقطة الدخول أو إعدادات النشر يتطلب موافقة صريحة على دفعة التحويل.
4. لا تُحذف النسخة القديمة أو بيانات النشاط والعضوية أثناء التحويل.
