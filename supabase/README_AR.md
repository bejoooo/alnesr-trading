# إعداد قاعدة البيانات — النسر للتجارة

> هذه ملفات تأسيس وتجهيز. لا تعتبر النظام جاهزًا للاستخدام التجاري قبل تطبيقها على مشروع تجريبي واجتياز اختبارات الحسابات والصلاحيات.

## الملفات وترتيب التنفيذ

1. `schema.sql` — إنشاء الجداول الأساسية والعلاقات الأولية وسياسات عزل بيانات الأنشطة.
2. `002_access_control.sql` — استبدال صلاحيات الوصول العامة بصلاحيات حسب الدور، ومنع المدير الإداري من ترقية نفسه أو غيره إلى مالك.
3. `003_atomic_business_operations.sql` — عمليات ذرية للمشتريات والمبيعات والدفعات والإيداع والمصروفات.
4. `004_tenant_integrity.sql` — قيود علاقات تمنع ربط سجلات بين نشاطين مختلفين.

نفّذ الملفات الأربعة بالترتيب من SQL Editor داخل مشروع Supabase جديد وتجريبي. لا تنفّذها على قاعدة بيانات تحتوي بيانات حقيقية.

## الأدوار الافتراضية

- **owner / admin:** إدارة كاملة. تعيين owner أو admin محصور بمالك النشاط.
- **manager:** إدارة العمليات اليومية (المنتجات، الأطراف، المشتريات، المبيعات، الدفعات، المخزون، المصروفات والخزنة) دون إدارة الأعضاء أو إعدادات النشاط الحساسة أو حذف السجلات افتراضيًا.
- **cashier:** عمليات البيع والتحصيل والحركات النقدية المسموح بها، مع عرض البيانات اللازمة.
- **viewer:** عرض فقط.

يمكن تجاوز الصلاحيات الافتراضية لكل عضو بمفاتيح Boolean داخل `business_members.permissions`. قيمة `true` تمنح الإذن المحدد، و`false` تمنعه. أسماء الأذونات المستخدمة في السياسات هي بصيغة مثل `sales.view` و`sales.create` و`sales.edit` و`sales.delete`.

## العمليات التي أصبحت لها واجهات قاعدة بيانات ذرية

- `post_purchase`: فاتورة مشتريات متعددة البنود، توزيع خصم المورد، تحديث متوسط التكلفة، حركة المخزون، والدفعة النقدية الأولى.
- `post_sale`: فاتورة مبيعات متعددة البنود، التحقق من توافر المخزون، حفظ تكلفة البيع والضمان، حركة المخزون والتحصيل النقدي الأول.
- `record_invoice_payment`: تحصيل أو سداد لاحق جزئي أو كامل، مع تحديث المتبقي وحركة الخزنة عند اختيار النقد.
- `record_cash_deposit`: إيداع نقدي بسبب واضح.
- `record_expense`: تسجيل مصروف وحركة صرف خزنة في معاملة واحدة.

هذه الدوال لم تُختبر بعد على خادم PostgreSQL/Supabase فعلي، ولا تغطي المرتجعات أو كل حالات التسوية المحاسبية حتى الآن.

## تنبيهات مهمة قبل الربط بالواجهة

- لا تضع مفتاح `service_role` في كود المتصفح أو GitHub.
- مفاتيح العميل العامة لا تكفي وحدها لحماية البيانات؛ الحماية الفعلية تعتمد على RLS والسياسات واختبارات المستخدمين.
- لا تنشئ دفعة أو فاتورة أو حركة مخزون من الواجهة على شكل عدة طلبات منفصلة قبل بناء عمليات قاعدة بيانات ذرية (RPC/transactions).
- يجب إضافة قيود تمنع ربط فاتورة أو منتج أو دفعة بسجل تابع لنشاط آخر، واختبارها صراحةً.
- يجب اختبار خصم المورد الموزع نسبيًا، ومتوسط التكلفة المرجح، والتحصيل والسداد الجزئي، والمرتجع الصالح والتالف، ومطابقة رصيد الخزنة.
- لا تستورد بيانات النسخة المحلية قبل بناء أداة ترحيل ومراجعة الأرصدة والكميات.

## حالة التنفيذ

الواجهة الحالية ما زالت النسخة المحلية القديمة. لا يوجد حتى الآن ربط فعلي بـ Supabase أو تسجيل دخول مركزي أو مزامنة بين الأجهزة. هذه الخطوة تأتي بعد مراجعة المخطط، واختبار SQL، ثم إعداد مشروع Supabase ومفاتيح العميل العامة بطريقة آمنة.
