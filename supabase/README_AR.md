# إعداد قاعدة البيانات — النسر للتجارة

> هذه ملفات تأسيس وتجهيز. لا تعتبر النظام جاهزًا للاستخدام التجاري قبل تطبيقها على مشروع تجريبي واجتياز اختبارات الحسابات والصلاحيات.

## الملفات وترتيب التنفيذ

1. `schema.sql` — إنشاء الجداول الأساسية والعلاقات الأولية وسياسات عزل بيانات الأنشطة.
2. `002_access_control.sql` — استبدال صلاحيات الوصول العامة بصلاحيات حسب الدور، ومنع المدير الإداري من ترقية نفسه أو غيره إلى مالك.
3. `003_atomic_business_operations.sql` — عمليات ذرية للمشتريات والمبيعات والدفعات والإيداع والمصروفات.
4. `004_tenant_integrity.sql` — قيود علاقات تمنع ربط سجلات بين نشاطين مختلفين.
5. `005_sales_returns.sql` — مرتجعات المبيعات، رد النقد، وتسوية رصيد العميل وإرجاع الصالح فقط للمخزون.
6. `006_invoice_reference_integrity.sql` — منع ربط الدفعات وحركات الخزنة بفواتير تابعة لنشاط آخر.
7. `007_stock_cash_reporting.sql` — تسويات المخزون، الرصيد الافتتاحي للخزنة، السحب النقدي، وأرصدة وتقارير يومية.
8. `008_party_accounts_reporting.sql` — أرصدة العملاء والموردين وكشوف الحساب.
9. `009_party_opening_balances.sql` — تحديد طبيعة الرصيد الافتتاحي (مستحق لنا/مستحق علينا) وحمايته بعد بدء التعامل.
10. `010_product_images_storage.sql` — إنشاء bucket خاص لصور المنتجات مع حد 5 ميجابايت وسياسات حسب صلاحيات النشاط.
11. `011_backup_restore.sql` — استعادة بيانات النشاط من نسخة JSON بواسطة المالك فقط، إلى نشاط مطابق وفارغ دون الكتابة فوق بيانات قائمة.
12. `012_secure_rpc_and_payment_reporting.sql` — تقوية صلاحيات تنفيذ الدوال الداخلية وتصحيح تصنيف دفعات التقارير اليومية.
13. `013_staff_management.sql` — دوال آمنة لعرض أعضاء النشاط وإضافة حساب موظف مؤكد البريد بواسطة المالك فقط.
14. `014_membership_privacy.sql` — قصر قراءة جدول العضويات على العضو نفسه.
15. `015_membership_policy_performance.sql` — فصل سياسات القراءة والكتابة للعضويات وتحسين تقييم auth.uid() في سياسات RLS.
16. `016_foreign_key_indexes.sql` — إضافة فهارس داعمة للمفاتيح الأجنبية لتحسين الربط والتحقق من العلاقات مع نمو البيانات.
17. `017_payment_visibility_by_invoice_permission.sql` — قصر قراءة الدفعات على نوع الفاتورة التي يملك المستخدم صلاحية عرضها، مع إبقاء السجلات غير المرتبطة بالفواتير للمالك والمدير فقط.
18. `018_owner_only_staff_management.sql` — فرض إدارة عضويات الموظفين للمالك فقط على مستوى RLS، ومنع المدير من تجاوز الواجهة وتعديل الموظفين مباشرة.
19. `019_restrict_direct_master_data_writes.sql` — تقييد الكتابة المباشرة على الأعمدة الحساسة للمنتجات والحسابات وبيانات النشاط، وتمرير تحديث الموظفين عبر RPC يتحقق من المالك.
20. `020_revoke_destructive_api_privileges.sql` — إلغاء صلاحيات الحذف وTRUNCATE وإنشاء المفاتيح والمشغلات من أدوار API على جداول وواجهات schema public؛ لا توجد وظيفة حذف مباشرة في التطبيق.
21. `021_party_opening_balance_integrity.sql` — ضبط اتجاه الرصيد الافتتاحي تلقائيًا حسب نوع العميل/المورد، وقفل سجل الحساب أثناء ترحيل أول فاتورة لمنع سباق تعديل الرصيد.
22. `022_fix_invoice_party_lock_trigger.sql` — إصلاح فحص نوع سجل العميل/المورد في trigger قفل الفواتير.
23. `023_customer_return_average_cost.sql` — إعادة حساب متوسط التكلفة المرجح عند رجوع منتج صالح للمخزون، باستخدام تكلفة الوحدة المحفوظة وقت البيع.
24. `024_revoke_trigger_function_execute.sql` — سحب صلاحية استدعاء دوال المشغلات الداخلية مباشرة من أدوار API مع إبقائها مرتبطة بالمشغلات فقط.
25. `025_revoke_remaining_trigger_function_execute.sql` — سحب صلاحية الاستدعاء المباشر من مشغلي حماية العضويات ومتوسط تكلفة المنتج.
26. `026_safe_default_api_privileges.sql` — منع منح صلاحيات الحذف وTRUNCATE والمشغلات والمفاتيح وMAINTAIN افتراضيًا للجداول الجديدة التي ينشئها دور postgres، وإلغاء EXECUTE الافتراضي لدواله.
27. `027_revoke_global_public_function_execute.sql` — إلغاء منح EXECUTE العام الافتراضي لدوال postgres الجديدة؛ لأن إلغاءه على مستوى schema وحده لا يلغي الامتياز العام الموروث.
28. `028_rpc_only_ledger_writes.sql` — منع الكتابة المباشرة من API على فواتير البيع والشراء وبنودها والدفعات والخزنة والمخزون والمصروفات وسجل المراجعة وإعدادات النسخ.
29. `029_read_only_defaults_for_new_tables.sql` — جعل الجداول العامة الجديدة للقراءة فقط من أدوار API افتراضيًا، ولا تُمنح صلاحيات الكتابة إلا صراحةً في migration.

نفّذ ملفات التأسيس من `schema.sql` حتى `011_backup_restore.sql` بالترتيب على مشروع Supabase تجريبي فارغ، ثم شغّل `verify_setup.sql`. بعد ذلك يمكن تطبيق `012` حتى `029` بالترتيب بعد مراجعة كل ملف. لا تنفّذها على قاعدة بيانات تحتوي بيانات حقيقية.

## الأدوار الافتراضية

- **owner / admin:** إدارة كاملة. تعيين owner أو admin محصور بمالك النشاط.
- **manager:** إدارة العمليات اليومية (المنتجات، الأطراف، المشتريات، المبيعات، الدفعات، المخزون، المصروفات والخزنة) دون إدارة الأعضاء أو إعدادات النشاط الحساسة أو حذف السجلات افتراضيًا.
- **cashier:** عمليات البيع والتحصيل والحركات النقدية المسموح بها، مع عرض البيانات اللازمة.
- **viewer:** عرض فقط.

يمكن تجاوز الصلاحيات الافتراضية لكل عضو بمفاتيح Boolean داخل `business_members.permissions`. قيمة `true` تمنح الإذن المحدد، و`false` تمنعه. أسماء الأذونات المستخدمة في السياسات هي بصيغة مثل `sales.view` و`sales.create` و`sales.edit` و`sales.delete`.

## العمليات التي أصبحت لها واجهات قاعدة بيانات ذرية

- `post_purchase`: فاتورة مشتريات متعددة البنود، توزيع خصم المورد، تحديث متوسط التكلفة، حركة المخزون، والدفعة النقدية الأولى.
- `post_sale`: فاتورة مبيعات متعددة البنود، التحقق من توافر المخزون، حفظ تكلفة البيع والضمان، حركة المخزون والتحصيل النقدي الأول.
- `record_invoice_payment`: تحصيل أو سداد لاحق جزئي أو كامل، مع تحديث المتبقي وحركة الخزنة عند اختيار النقد.
- `record_cash_deposit`: إيداع نقدي بسبب واضح.
- `record_expense`: تسجيل مصروف وحركة صرف خزنة في معاملة واحدة.
- `post_sales_return`: ربط المرتجع ببند الفاتورة، منع تجاوز الكمية المباعة، إعادة الصالح فقط للمخزون، وتسوية المستحق أو رد النقد.
- `post_stock_adjustment`: تسوية كمية المخزون بسبب جرد أو زيادة/عجز مع منع الرصيد السالب وتحديث متوسط التكلفة عند الزيادة.
- `record_cash_opening_balance`: تسجيل رصيد افتتاحي مرة واحدة قبل أول حركة خزنة.
- `record_cash_withdrawal`: صرف نقدي بسبب واضح مع منع الصرف بأكثر من الرصيد المتاح.
- `set_party_opening_balance`: تسجيل رصيد افتتاحي للعميل أو المورد قبل بدء حركات الحساب.

ملف `verify_setup.sql` يفحص وجود المكونات الأساسية فقط؛ لا ينفّذ سيناريوهات معاملات فعلية. تم اختبار سيناريوهات معاملات مؤقتة على مشروع Supabase تجريبي، مع حذف بيانات الاختبار بعد انتهائها؛ لكن ذلك لا يغني عن اختبار الواجهة بحسابات وأجهزة فعلية. عرض `product_stock_balances` و`cash_balances` يوفر أرصدة المخزون والخزنة، و`daily_business_summary` يوفر تجميعًا يوميًا للتواريخ التي بها حركات؛ يمكن تجميعه أسبوعيًا أو شهريًا في طبقة التقارير بعد اختبار النتائج. كما يوفر `party_account_balances` رصيد كل عميل/مورد، و`party_account_statement` تفاصيل كشف الحساب.

## تنبيهات مهمة قبل الربط بالواجهة

- لا تضع مفتاح `service_role` في كود المتصفح أو GitHub.
- مفاتيح العميل العامة لا تكفي وحدها لحماية البيانات؛ الحماية الفعلية تعتمد على RLS والسياسات واختبارات المستخدمين.
- لا تنشئ دفعة أو فاتورة أو حركة مخزون من الواجهة على شكل عدة طلبات منفصلة قبل بناء عمليات قاعدة بيانات ذرية (RPC/transactions).
- يجب إضافة قيود تمنع ربط فاتورة أو منتج أو دفعة بسجل تابع لنشاط آخر، واختبارها صراحةً.
- يجب اختبار خصم المورد الموزع نسبيًا، ومتوسط التكلفة المرجح، والتحصيل والسداد الجزئي، والمرتجع الصالح والتالف، ومطابقة رصيد الخزنة.
- لا تستورد بيانات النسخة المحلية قبل بناء أداة ترحيل ومراجعة الأرصدة والكميات.

## حالة التنفيذ

واجهة `app/` الحالية مجهزة بوحدات التشغيل والربط البرمجي بـ Supabase Auth وDatabase وStorage. تم تشغيل ملفات `schema.sql` و`002` حتى `016` على مشروع Supabase تجريبي، واجتاز فحص التحقق الهيكلي واختبارات معاملات مؤقتة تُحذف بياناتها في نهاية الاختبار. تم التحقق من تغطية الفهارس لجميع المفاتيح الأجنبية الـ53. أضيفت Migration 017 لتقييد رؤية الدفعات حسب صلاحيات قسم الفاتورة، وMigration 018 لفرض إدارة الموظفين للمالك فقط على مستوى RLS. لم يكتمل اختبار المتصفح الشامل أو اختبار حساب موظف منفصل؛ لا تدخل بيانات تجارية حقيقية قبل إتمامهما.

## سجل تطبيق migrations

تم تنفيذ ملفات التأسيس الأولى وملفات `012` و`014` يدويًا من SQL Editor؛ لذلك لا تظهر هذه العمليات القديمة كسجلات مستقلة في جدول `supabase_migrations.schema_migrations`. أما العمليات التي نُفذت عبر أداة تطبيق migrations فتظهر في السجل، ومنها `013` (مسجل باسم `staff_management`) و`015` إلى `018`. هذا اختلاف في طريقة تسجيل تاريخ التنفيذ، وليس دليلًا وحده على أن التعديلات غير موجودة. لا تُضف سجلات تاريخية يدويًا ولا تُعد تشغيل ملفات التأسيس على قاعدة تحتوي بيانات؛ المرجع للتحقق من الحالة الفعلية هو تعريفات الجداول والسياسات والدوال وفحوص `verify_setup.sql`.

## سجل المراجعة

جدول `audit_log` محمي بسياسة قراءة تتطلب `audit.view`، ولا توجد سياسة كتابة مباشرة للمستخدمين المسجلين. لا توجد حاليًا شاشة داخل التطبيق لعرض سجل المراجعة؛ صلاحية العرض موجودة في قاعدة البيانات وإعدادات الأدوار فقط، وتحتاج واجهة مستقلة قبل اعتبار الميزة مكتملة.

## النسخ الاحتياطي والاستعادة

- النسخة JSON تشمل بيانات الجداول التشغيلية الأساسية للنشاط، ولا تشمل سجل التدقيق أو ملفات الصور الفعلية داخل Storage.
- الاستعادة لا تحذف ولا تستبدل بيانات؛ ترفض التنفيذ إذا كان أي جدول مستهدف يحتوي سجلات. يجب أن يكون ملف النسخة من نفس `business_id` وأن ينفذها مالك النشاط.
- بعد استعادة قاعدة البيانات، تظل ملفات الصور متاحة فقط إذا بقيت موجودة في bucket الخاص بها. احتفظ بنسخة مستقلة من ملفات Storage إذا كنت تريد حماية الصور أيضًا.


## إدارة الموظفين وإعدادات النشاط

- شاشة إعدادات النشاط تعرض الاسم والهاتف والعنوان؛ تعديل هذه البيانات متاح للمالك والمدير وفق سياسات قاعدة البيانات.
- إدارة الموظفين متاحة لمالك النشاط فقط. يجب أن ينشئ الموظف حسابًا ويؤكد بريده قبل أن يضيفه المالك باستخدام البريد الإلكتروني.
- دوال `list_business_members` و`add_business_member_by_email` تتحقق من هوية المالك النشط داخل قاعدة البيانات، ولا تعتمد على إخفاء عناصر الواجهة وحده.
- يمكن للمالك تغيير دور الموظف بين مشرف وكاشير ومشاهدة فقط، وتخصيص صلاحياته وإيقاف عضويته. لا يمكن عبر الشاشة إنشاء مالك إضافي أو تغيير المالك الحالي.


### Migration 019

- تم تطبيقها على مشروع الاختبار `alnesr-trading-test` بنجاح.
- أُلغيت صلاحيات الكتابة العامة على جداول `businesses` و`products` و`parties` و`business_members`، ثم مُنحت صلاحيات الأعمدة اللازمة فقط للواجهة.
- لم يعد بإمكان مستخدم الواجهة تعديل متوسط تكلفة المنتج أو هوية النشاط/المنتج أو حالة المنتج، ولا أرصدة الحسابات الافتتاحية، ولا هوية منشئ النشاط.
- تعديلات الموظفين تمر الآن عبر `update_business_member` التي تتحقق من أن المنفذ هو المالك النشط، وتمنع تعديل عضوية owner/admin والتحقق من مفاتيح الصلاحيات وقيمها.
- تم تحديث الواجهة لاستدعاء RPC بدل تحديث `business_members` مباشرة.
- يلزم استكمال اختبارات الكتابة الفعلية بحساب مالك وموظف منفصل في الاختبار الشامل؛ فحص الصلاحيات الهيكلي وحده لا يثبت كل المسارات.


### Migration 020

- تم تطبيقها على مشروع الاختبار بنجاح بعد التحقق من الجداول والـ views معًا.
- أُلغيت من أدوار `anon` و`authenticated` صلاحيات `DELETE` و`TRUNCATE` و`REFERENCES` و`TRIGGER` على كل العلاقات في `public`، بما فيها واجهات التقارير.
- فحص الامتيازات بعد التطبيق أعاد صفر صلاحيات متبقية من الأنواع الأربعة.
- هذا لا يمنع العمليات المحاسبية المصرح بها داخل دوال `SECURITY DEFINER`؛ بل يمنع الوصول المباشر لهذه العمليات من خلال صلاحيات الجداول.


### Migration 021 و022

- Migration 021 تضبط `opening_balance_side` تلقائيًا إلى `receivable` للعميل وإلى `payable` للمورد، وتضيف أقفال صفوف عند إدراج فواتير البيع والشراء حتى لا يتزامن بدء التعامل مع تعديل الرصيد الافتتاحي.
- Migration 022 تصلح التفرع حسب نوع جدول الفاتورة داخل trigger؛ تم اختبار إدراج مورد وعميل مؤقتين، والتحقق من اتجاه الرصيد الافتراضي، ورفض ربط فاتورة بيع بمورد أو فاتورة شراء بعميل، والسماح بربط المورد الصحيح. كل بيانات الاختبار كانت داخل معاملة تم التراجع عنها.
- لم تتغير بيانات النشاط الفعلية خلال هذه الاختبارات.


### Migration 023

- تم إصلاح نقطة في تقييم المخزون: المرتجع الصالح كان يضيف كمية للمخزون بتكلفة البيع الأصلية، لكنه لا يعيد حساب متوسط التكلفة الحالي.
- أضيف trigger يعيد حساب المتوسط المرجح بعد إضافة حركة `customer_return_good`، مع قفل سجل المنتج لحماية الحساب عند تزامن المرتجعات.
- اختبار مؤقت: رصيد 20 وحدة بمتوسط 15 ج.م، ثم إرجاع وحدة بتكلفة 10 ج.م؛ المتوسط الجديد تحقق = 14.76 ج.م. تم التراجع عن معاملة الاختبار ولم يبقَ منتج اختبار.


### Migration 024

- سُحبت صلاحيات `EXECUTE` من `PUBLIC` و`anon` و`authenticated` عن دوال المشغلات الثلاث التي أُنشئت في 021 و023؛ هذه الدوال تُنفّذ فقط ضمن trigger ولا يحتاج المتصفح إلى استدعائها.
- اجتاز فحص الامتيازات بعد التطبيق، ويجب أن تستمر اختبارات عمليات الفواتير والمرتجعات في التأكد من عمل المشغلات داخليًا.


### Migration 025

- أُلغيت صلاحية التنفيذ المباشر لدالتي trigger `guard_business_member_changes` و`guard_product_average_cost` من أدوار API؛ تظل المشغلات نفسها تعمل أثناء عمليات قاعدة البيانات.
- فحص دوال المشغلات بعد 024 و025 أكد أن أدوار API لا تستطيع استدعاء دوال trigger مباشرة.
- تم اختبار إنشاء نشاط مؤقت بحساب المالك داخل معاملة متراجَع عنها؛ أُنشئت عضوية المالك تلقائيًا عبر trigger، دون الحاجة لصلاحية تنفيذ مباشرة على دالة trigger.


### Migration 026

- أُلغيت الامتيازات غير اللازمة على العلاقات الحالية، بما فيها `MAINTAIN`، وأصبح هذا الإلغاء افتراضيًا للكائنات الجديدة التي ينشئها دور `postgres` داخل `public`.
- أُلغي منح `EXECUTE` الافتراضي على الدوال الجديدة التي ينشئها `postgres`؛ يجب منح التنفيذ صراحةً فقط لدوال RPC المقصودة.

## تنبيه مهم — اختلاف حالة الإنتاج عن سجل الاختبار (25 نوفمبر 2026)

هذا الدليل يشرح التأسيس المبكر ولا يمثل خطة ترقية للإنتاج الحالي. قاعدة الاختبار تحتوي 118 سجل Migration، بينما الإنتاج يحتوي 19 سجلًا فقط، مع اختلاف في أسماء الترحيلات وبعض تعريفات الجداول والدوال والـViews والـRLS والـTriggers. كما توجد ترحيلات تشغيلية مسجلة في الاختبار لم يعد ملف SQL الأصلي لها موجودًا في المستودع.

**ممنوع تشغيل ملفات `supabase/*.sql` بالتتابع على قاعدة الإنتاج اعتمادًا على أرقامها أو هذا الدليل.** لا تُشغّل `schema.sql` أو `reset` أو `restore` على الإنتاج، ولا تنشئ جداول/قيود/دوال قبل مطابقة حالتها الحالية وبياناتها. يلزم تجهيز حزمة ترقية additive خاصة بالإنتاج، والتحقق منها على بيئة مجانية معزولة إن توفرت دون إنشاء مشروع/فرع مدفوع، ثم أخذ نسخة احتياطية قابلة للاسترجاع وإجراء مراجعة نهائية قبل أي تطبيق.

حتى تاريخ هذا التحديث، لم تُطبق أي تغييرات SQL على قاعدة الإنتاج ضمن مراجعة الانتقال، ولم تُجهز حزمة ترقية تنفيذية نهائية. تبقى قاعدة الاختبار وملفات Preview كما هي، ويجب الحفاظ على بيانات النشاط والعضوية الموجودة بالإنتاج.


### مراجعة تعريفات العمليات المالية الحرجة من كتالوج Test (25 نوفمبر 2026)

تم استخراج التعريف الحالي مباشرة من PostgreSQL للدوال الخاصة بمرتجعات المشتريات والتحويلات بين وسائل الدفع، ومراجعة خصائصها وامتيازات تنفيذها:

- الدوال التي تمت مراجعتها: `post_purchase_return_with_settlement` و`owner_void_purchase_return` و`receive_supplier_credit` و`create_treasury_transfer` و`reverse_treasury_transfer`.
- جميعها `SECURITY DEFINER` بمالك `postgres` و`search_path` فارغ؛ وكل مراجع الجداول والدوال داخل التعريفات مؤهلة باسم schema. امتياز التنفيذ: `authenticated=true` و`anon=false` و`PUBLIC=false` لكل التواقيع الخمسة.
- مرتجع المشتريات لا يقتصر على إنشاء رأس وبنود: يسجل حركة مخزون سالبة مع فصل `sellable/damaged`، ويعيد حساب متوسط التكلفة، ويخفض مستحق فاتورة المورد، ويسجل الاسترداد كدفعة وحركة خزنة عند الدفع النقدي، أو ينشئ رصيدًا دائنًا للمورد عند تأجيل الاستلام/وجود رصيد سابق.
- إلغاء مرتجع المشتريات يفحص ترتيب الحركات اللاحقة، وتطابق بنود المرتجع مع حركات المخزون، وعدم استخدام رصيد المورد الدائن لاحقًا، ثم يعكس حركات المخزون والدفعات والخزنة ويعيد مستحق الفاتورة. ويرفض الإلغاء الآلي إذا كانت لقطة توزيع المستحق القديمة غير موجودة.
- التحويل بين وسائل الدفع يقفل النشاط بقفل advisory، ويتحقق من الرصيد المتاح في وسيلة المصدر، ثم يسجل التحويل وحركة الخزنة إذا كان أحد الطرفين نقديًا وسجل التدقيق. العكس ينشئ تحويلًا عكسيًا مرتبطًا بالأصل، ويرفض العكس المكرر أو غير المتاح رصيده.
- هذه التعريفات تعتمد مباشرة على بنية `purchase_returns` و`purchase_return_items` و`treasury_transfers` وحقول الربط والعكس في `payments` و`cash_transactions` و`stock_movements`، وعلى Views الأرصدة، ودوال `has_business_permission` و`next_operation_code`، و`audit_log`. لذلك لا يمكن ترحيلها قبل اكتمال هذه الاعتماديات وسياسات RLS والقيود والفهارس والمشغلات.

**قيد مهم على التحقق:** فحص الكتالوج يؤكد التعريفات وخصائص الأمان وامتيازات التنفيذ فقط؛ لم نشغّل عمليات مرتجع أو تحويل أو عكس فعلية في هذه الجولة، ولم نكتب أي بيانات أو DDL على Test أو Production. كما أن وجود التعريف في Test لا يثبت وحده أن كل backfill تاريخي مفقود قد أُعيد بناؤه.


### مراجعة الدفعات وعكسها والرصيد الدائن للعميل (25 نوفمبر 2026)

تم استخراج التعريفات الحالية من قاعدة Test للدوال: `record_invoice_payment` و`record_standalone_party_payment` و`owner_reverse_invoice_payment` و`owner_reverse_customer_invoice_payment` و`owner_reverse_standalone_party_payment` و`pay_customer_credit`، ومراجعة خصائص التنفيذ:

- التواقيع الستة كلها `SECURITY DEFINER` مع `search_path` فارغ؛ صلاحية التنفيذ `authenticated=true` و`anon=false` و`PUBLIC=false`.
- تسجيل دفعة الفاتورة يقفل النشاط، ويتحقق من نوع الفاتورة وحالتها والمبلغ المستحق والصلاحية، ويفحص رصيد وسيلة الدفع عند سداد المورد. الدفعة النقدية تنشئ حركة خزنة مرتبطة بمعرف الدفعة، ثم تحدث المدفوع والمتبقي وتسجل الحدث في `audit_log`.
- الدفعات المستقلة تتحقق من نوع حساب العميل/المورد ونوع الطرف وحالة الحساب والصلاحيات، وتتحقق من رصيد وسيلة الدفع عند الصرف. كما تربط الدفعة النقدية بحركة خزنة من خلال `payment_id`.
- عكس دفعة فاتورة المورد أو العميل ينشئ دفعة مقابلة مرتبطة بالأصل عبر `reversal_of_payment_id` ويحدث إجماليات الفاتورة. وفي الحالة النقدية يشترط وجود حركة خزنة أصلية واحدة مطابقة قبل إنشاء الحركة العكسية وربط الأصل.
- عكس الدفعة المستقلة يعكس اتجاه الدفعة وحركة الخزنة، ويعالج أحداث صرف الرصيد الدائن للعميل بإضافة حدث عكسي مرتبط بالأصل عبر `reversal_of_id`. ويمنع العكس المكرر.
- `pay_customer_credit` يقفل النشاط وحساب العميل، ويتحقق من الرصيد الدائن المتاح ورصيد وسيلة الدفع، ثم يوزع الصرف على مصادر الرصيد حسب أقدمية المصدر، ويسجل دفعة وحركات دفتر الرصيد، وحركة خزنة عند الدفع نقدًا.
- سياسة قراءة `customer_credit_ledger` في Test تسمح للمستخدم المصادق الذي يملك `sales.view` أو `parties.view`. وسياسة `payments_read` تربط قراءة الدفعات المستقلة بصلاحية `payments.view` مع صلاحية عرض حساب العميل أو المورد، وتُبقي الدفعات القديمة التي لا تحمل `party_account_type` للمالك/المدير فقط.

**اعتماديات الترقية التي لا يجوز فصلها:** أعمدة الربط والعكس في `payments` و`cash_transactions`، وجدول `customer_credit_ledger` مع `reversal_of_id`، وحقول أرصدة الفواتير، وViews `cash_balances` و`customer_credit_balances` و`customer_credit_return_balances`، وسياسات RLS، وقيود منع العكس المكرر، وTriggers الترقيم. كما يجب التحقق من توافق سياسة `payments_read` في الإنتاج قبل استبدالها؛ لا تُنقل السياسة دون مراجعة صلاحيات الموظفين الحالية.

**حدود الاختبار:** هذه مراجعة ساكنة لتعريفات الدوال والسياسات والامتيازات في Test، وليست تجربة تشغيل فعلية. لم يتم إنشاء دفعات أو عكسها، ولم تتغير أرصدة أو بيانات في أي قاعدة. ولم يُثبت هذا الفحص وحده اكتمال أي backfill تاريخي مفقود.


### مراجعة البيع ومرتجعات المبيعات وإلغاء الفواتير (25 نوفمبر 2026)

تمت مراجعة تواقيع وخصائص الأمان لدوال `post_sale_with_method` (نسختان overload)، و`post_sales_return` (نسختان overload)، و`owner_void_invoice`، و`owner_remove_sales_return`، و`post_stock_condition_transfer` في Test:
- كل التواقيع التي فُحصت تستخدم `SECURITY DEFINER` مع `search_path` فارغ؛ التنفيذ مسموح لـ`authenticated` وممنوع عن `anon` و`PUBLIC`.
- دالة إلغاء الفاتورة تشترط المالك النشط، وتقفل النشاط والفاتورة، وترفض إلغاء فاتورة بيع عليها مرتجعات نشطة، وتتحقق من استخدام الرصيد الدائن، وترفض الإلغاء إذا وجدت حركات مخزون لاحقة. كما تطابق إجمالي الدفعات النقدية مع سجل الخزنة قبل العكس، وتتحقق من توفر النقدية قبل عكس المقبوضات النقدية.
- دالة إلغاء مرتجع المبيعات تتحقق من ترتيب المرتجعات والدفعات اللاحقة، وتمنع الإلغاء إذا استُخدم رصيد المرتجع أو صُرف، وتطابق سجل رد النقدية مع سجل الدفعة، وتتحقق من الكميات المعادة وحركات المخزون القابل للبيع والتالف. وتحتاج `average_cost_before` لإرجاع متوسط التكلفة؛ إذا لم تتوفر لقطة التكلفة في حركة قديمة ترفض الإلغاء بدل تخمين التكلفة.
- إلغاء المرتجع يعكس دفعة رد المبلغ وحركة الخزنة وحركات المخزون، ويعكس رصيد العميل الدائن، ويعيد كميات البنود إلى وضعها السابق، ثم يحدث حالة المرتجع والفاتورة ويسجل الحدث في `audit_log`.
- بنية الجداول التي تعتمد عليها هذه العمليات تشمل `sales_returns.status` و`posted_at` و`invoice_due_reduced_total`، و`sales_return_items.unit_price`، و`sales_invoices.customer_credit_applied_total`، وروابط العكس في `payments` و`cash_transactions` و`stock_movements`، مع فصل `sellable/damaged` ولقطة `average_cost_before`.

**ترتيب الاعتماديات:** لا تنقل دوال البيع والإلغاء قبل أعمدة الربط والعكس، ودفتر رصيد العميل الدائن، وحقول حالة المرتجع وتوقيت الترحيل، ولقطات التكلفة، وViews الأرصدة، وقيود منع العكس المكرر، وسياسات RLS وTriggers الترقيم. كما يجب فحص كل overload على حدة حتى لا يُستبدل توقيع أحدث بتوقيع قديم.

**حدود الفحص:** خصائص الأمان والتواقيع جرى التحقق منها من الكتالوج. تمت قراءة منطق إلغاء الفاتورة وإلغاء مرتجع المبيعات ساكنًا؛ لم تُنشأ فاتورة أو مرتجع ولم تُنفذ عملية عكس أو حركة مخزون، ولم تتغير بيانات Test أو Production. لا يُعد ذلك اختبار تشغيل فعليًا ولا يثبت استعادة أي backfill تاريخي.


### مراجعة المخزون والتكلفة وتسويات الحالة (25 نوفمبر 2026)

تمت مراجعة دوال `post_stock_adjustment` و`post_stock_condition_transfer` و`owner_reverse_stock_adjustment`، وكذلك مسار حساب التكلفة داخل `post_purchase_with_method` وخصم المخزون داخل `post_sale_with_method`.

**الأمان والصلاحيات**
- الدوال الثلاث الخاصة بتسوية المخزون ونقل حالته تستخدم `SECURITY DEFINER` و`search_path` فارغًا؛ EXECUTE مسموح لـ`authenticated` وممنوع عن `anon` و`PUBLIC`.
- التسوية ونقل الحالة يشترطان `inventory.create`، بينما عكس التسوية مقصور على المالك النشط للنشاط.
- الدوال تقفل النشاط/المنتج قبل تعديل حركاته، وتتحقق من انتماء المنتج للنشاط ومن عدم تجاوز الكمية المتاحة في المخزن/الحالة المحددة.

**السلوك الذي تمت مراجعته**
- تسوية الزيادة/النقص تسجل حركة موثقة في `stock_movements` مع سبب، وتحتفظ بلقطة `average_cost_before` في `stock_adjustment_cost_snapshots`. الزيادة تحسب متوسط تكلفة جديدًا؛ النقص لا يغير متوسط التكلفة.
- نقل الحالة بين `sellable` و`damaged` ينشئ حركتين متساويتين ومتعاكستين للمنتج نفسه، ولا يغير إجمالي الكمية أو متوسط التكلفة. ويتحقق من رصيد الحالة المصدر.
- عكس التسوية يمنع العكس المكرر، ويرفض العملية عند وجود حركات لاحقة للمنتج أو عدم كفاية الرصيد. وعند عكس زيادة مخزون يشترط وجود لقطة التكلفة السابقة ويعيد متوسط التكلفة منها.
- `stock_movements.stock_bucket` له default هو `sellable`، و`posted_at` يُسجل تلقائيًا. يوجد قيد فريد يمنع أكثر من حركة عكس واحدة للأصل، وفهارس للاستعلام حسب النشاط/المنتج/وقت الترحيل والحالة.

**نقطة تحتاج حسمًا قبل اعتماد حزمة الترقية (ليست إصلاحًا منفذًا):**
- `post_purchase_with_method` يحسب متوسط التكلفة باستخدام مجموع كل حركات المنتج دون تصفية `stock_bucket`، أي إن الكمية التالفة تدخل في مقام المتوسط.
- بالمقابل، `post_stock_adjustment` يحسب متوسط تكلفة الزيادة على رصيد `sellable` فقط. لذلك تختلف قاعدة احتساب المتوسط بين شراء جديد وتسوية زيادة مخزون عندما يكون للمنتج رصيد تالف.
- لا يمكن الجزم من التعريفات وحدها أن أحد المسارين خطأ؛ يلزم اعتماد قاعدة محاسبية واحدة: هل متوسط التكلفة يُحسب على كامل الكمية الفعلية (القابلة للبيع والتالفة) أم على القابلة للبيع فقط؟ يجب توحيد دوال الشراء والتسوية وفق القاعدة المعتمدة قبل نقلها إلى Production. لم يتم تغيير أي دالة في هذه المراجعة.

**حدود الفحص:** مراجعة ساكنة لتعريفات الدوال والقيود والفهارس والقيم الافتراضية فقط. لم تُنشأ تسوية أو حركة نقل حالة أو عملية عكس، ولم تتغير بيانات Test أو Production. لا يُعد ذلك اختبار تشغيل فعليًا.


**استكمال فحص حماية حركات المخزون والتريجرات:**
- قراءة `stock_movements` محكومة بسياسة `inventory.view`. لا توجد سياسات كتابة مباشرة للجداول الثلاثة الخاصة بحركات المخزون ولقطات التكلفة؛ مسارات الكتابة تمر عبر RPCs المراجعة.
- جدولَا لقطات تكلفة فواتير الشراء وتسويات المخزون لديهما سياسة قراءة للمالك فقط.
- Trigger `stock_movements_assign_code` يولد كود الحركة تلقائيًا عبر `next_operation_code`.
- Trigger `stock_movements_customer_return_average_cost` يحدّث متوسط التكلفة عند دخول مرتجع صالح للبيع، ويحفظ المتوسط السابق في `average_cost_before`. هذا المسار، مثل الشراء، يستخدم إجمالي حركات المنتج عبر الحالتين؛ ويؤكد ضرورة حسم قاعدة المتوسط الموحدة مع تسوية الزيادة اليدوية قبل ترقية الإنتاج.

### ملاحظات أمان من فحص Advisors للإنتاج
- فحص Advisors أظهر 17 دالة `SECURITY DEFINER` قابلة للتنفيذ بواسطة `authenticated`، إضافة إلى تحذير تعطيل حماية كلمات المرور المسرّبة. تحذير قابلية استدعاء الدالة من مستخدم مسجل ليس وحده إثبات ثغرة؛ بعض هذه الدوال واجهات RPC مقصودة. قبل الترقية يجب فحص جسم كل دالة للتأكد من `auth.uid()` والتحقق من عضوية النشاط والدور/الصلاحية ومنع الوصول بين الأنشطة، وعدم فتح EXECUTE لـ`anon` أو `PUBLIC`.

- لا تزال ترقية Production متوقفة على إعداد حزمة SQL additive ومراجعتها، وحسم قاعدة متوسط التكلفة، ثم أخذ موافقة صريحة قبل أول كتابة على قاعدة الإنتاج.


### تدقيق دقيق لمنح الجداول الجديدة وRLS (25 نوفمبر 2026)
- الجداول السبعة في Test كلها مفعّل عليها RLS.
- `operation_counters` لا تمنح `anon` أو `authenticated` أي صلاحيات مباشرة، ولا توجد لها Policy؛ وهذا مقصود لأن الوصول إليها يتم من دوال الترقيم الموثوقة فقط.
- جداول لقطات التكلفة تمنح `authenticated` صلاحية SELECT فقط، وسياساتها تقصر القراءة على المالك. لا توجد صلاحيات كتابة مباشرة للمستخدمين.
- `customer_credit_ledger` يمنح `authenticated` SELECT فقط، وسياسة القراءة تتطلب `sales.view` أو `parties.view`. لا توجد صلاحيات كتابة مباشرة.
- ظهر أن `anon` لديه GRANT SELECT مباشر على `purchase_returns` و`purchase_return_items` و`treasury_transfers`، مع أن سياسات RLS لهذه الجداول موجهة إلى `authenticated` فقط؛ لذلك لا تمنح سياسة RLS الحالية صفوفًا للمستخدم المجهول. هذا ليس دليلًا على تسريب صفوف، لكنه GRANT غير ضروري ويجب إزالة صلاحية `anon` منه عند إعداد حزمة Production، مع إعادة التحقق من عدم وجود وصول عبر دور آخر.
- لا تُنسخ هذه المنح حرفيًا دون مراجعة. معيار الترقية هو أقل صلاحيات ممكنة: `authenticated` للقراءة وفق سياسة النشاط والصلاحية، والكتابة عبر RPCs المعتمدة فقط، وعدم منح `anon` أو `PUBLIC` وصولًا مباشرًا.


**تفصيل مُحدّث لدوال SECURITY DEFINER في Production:** أظهر جرد الكتالوج 20 دالة SECURITY DEFINER في `public`: منها 17 قابلة للتنفيذ بواسطة `authenticated` (وهي مجموعة تحذير Advisor)، وصفر قابلة للتنفيذ بواسطة `anon` أو `PUBLIC`. الثلاث الباقية غير قابلة للاستدعاء من هذه الأدوار. من حيث إعداد `search_path`: 16 دالة تستخدم `public` أو `public, pg_temp`، و3 تستخدم مسارًا فارغًا، وواحدة تستخدم `pg_catalog`. لذلك نطاق المراجعة الأمنية ليس مجرد إزالة تحذير Advisor؛ بل مراجعة جسم كل واحدة من الـ17 القابلة للاستدعاء، ثم تضييق مسار البحث للدوال التي يمكن ضبطها بأمان بعد تثبيت أسماء الكائنات المؤهلة بالكامل.


### تثبيت مواصفات الجداول التشغيلية السبعة قبل كتابة SQL للترقية

تم استخراج تعريفات الأعمدة والمفاتيح والعلاقات من Test عبر كتالوج PostgreSQL وواجهات جرد الجداول، دون نسخ أي صفوف. المواصفات المرجعية:

| الجدول | المفتاح الأساسي | أهم الأعمدة والعلاقات |
|---|---|---|
| `purchase_invoice_cost_snapshots` | `(invoice_id, product_id)` | `business_id`, `average_cost_before`, `created_at`; يرتبط بفاتورة الشراء والمنتج |
| `stock_adjustment_cost_snapshots` | `(business_id, movement_id)` | `product_id`, `average_cost_before`, `created_at`; يرتبط بحركة المخزون والمنتج |
| `operation_counters` | `(business_id, operation_type)` | `last_number` غير سالب، `updated_at`; صف مستقل لكل نوع ترقيم داخل النشاط |
| `treasury_transfers` | `id` | تاريخ التحويل، وسيلة المصدر والوجهة، مبلغ موجب، كود التحويل، ورابط التحويل العكسي، والمنشئ؛ ترتبط بالنشاط وبحركات الخزنة |
| `purchase_returns` | `id` | رقم المرتجع، فاتورة الشراء، المورد، التاريخ، الإجمالي، الحالة، `posted_at`، الرصيد الدائن الناتج، والمبلغ الذي خفّض مستحق الفاتورة |
| `purchase_return_items` | `id` | المرتجع، بند الشراء الأصلي، المنتج، كمية موجبة، الحالة `good/damaged`, تكلفة الوحدة وإجمالي البند |
| `customer_credit_ledger` | `id` | العميل، مصدر الرصيد من المرتجع أو الفاتورة، الدفعة، نوع الحدث، مبلغ غير صفري، ورابط عكس فريد |

**ترتيب إنشاء العلاقات:** إنشاء الأعمدة المرجعية أولًا، ثم `purchase_returns` قبل `purchase_return_items`، وإنشاء `treasury_transfers` قبل إضافة FK الخاص به إلى `cash_transactions`، وإنشاء `customer_credit_ledger` بعد وجود `sales_returns` و`sales_invoices` و`payments`. جداول لقطات التكلفة تأتي بعد الجداول التي تشير إليها. يجب استخدام مفاتيح مركبة تمنع ربط سجل من نشاط بمنتج/فاتورة/حركة من نشاط آخر، وعدم الاكتفاء بمفاتيح منفردة حيث يوفر Test قيد same-business.

**بيانات Test الحالية التي لا تُنقل إلى Production:** لقطات تكلفة فواتير الشراء 9 صفوف، لقطات تسويات المخزون 0، تحويلات الخزنة 12، عدادات الترقيم 9، مرتجعات المشتريات 2، بنود مرتجعات المشتريات 2، ودفتر رصيد العميل الدائن 2. هذه بيانات اختبار/تطوير وليست seed data؛ لا تُنسخ ولا تُستورد. أرقام العدادات في Production يجب أن تبدأ أو تُهيأ من واقع سجلات Production بعد التحقق من عدم وجود أكواد مستخدمة، لا من عدادات Test.

**قيود ما قبل كتابة حزمة الترقية:** هذه المواصفات المرجعية لا تكفي وحدها لإنشاء migration نهائي؛ يجب إرفاق جميع القيود والفهارس وسياسات RLS والمنح وTriggers والدوال التي تعتمد على الجداول، ثم فحص تعارضات الأكواد والقيود في Production. لا تُنشأ الجداول السبعة بشكل منفصل عن حزمة الاعتماديات، ولا تُنفذ على Production قبل اكتمال SQL ومراجعته وموافقة المستخدم.


### تدقيق علاقات same-business وقابلية وصول Data API (25 نوفمبر 2026)

**مراجعة العلاقات المركبة**
- الجداول المرجعية في Test توفر مفاتيح فريدة مركبة مثل `(business_id,id)` في `products`, `parties`, `purchase_invoices`, `sales_invoices`, `sales_returns`، كما توفر `purchase_returns` و`treasury_transfers` و`customer_credit_ledger` مفاتيح مركبة مماثلة.
- رغم ذلك، عدد من Foreign Keys في الجداول التشغيلية الجديدة يشير إلى `id` فقط بدل `(business_id,id)`: منها ربط مرتجع الشراء بالمورد وفاتورة الشراء، وربط بنود المرتجع بالمرتجع وبند الشراء والمنتج، وروابط دفتر رصيد العميل بالفاتورة/الدفعة/المرتجع/العميل، وروابط لقطات التكلفة بالمنتج/الفاتورة/حركة المخزون. لذلك لا تفرض هذه القيود وحدها تطابق `business_id` بين الصفين.
- دوال RPC التي تمت مراجعتها تتحقق من النشاط والملكية/الانتماء قبل الكتابة، والجداول الجديدة لا تمنح المستخدمين صلاحية كتابة مباشرة. هذا يقلل مسارات الخطر الحالية، لكنه لا يعوض قيد سلامة مرجعي على مستوى قاعدة البيانات.
- في مسودة الترقية يجب إضافة مفاتيح فريدة مركبة ناقصة على الجداول المرجعية عند الحاجة، ثم إضافة Foreign Keys مركبة `(business_id, foreign_id)` إلى `(business_id,id)` حيث يمكن ذلك، مع فحص الصفوف الحالية أولًا. لا تُضفها عشوائيًا قبل التأكد من وجود الأعمدة والمفاتيح المركبة ومطابقة ترتيبها.
- توجد بعض الجداول مثل `purchase_items` و`payments` و`stock_movements` لا تظهر لها حاليًا مفاتيح فريدة مركبة `(business_id,id)` في الكتالوج؛ يلزم إضافة المفاتيح المناسبة قبل ربطها بعلاقات مركبة، أو إبقاء التحقق الصريح داخل RPC إذا كان تغيير المفتاح المرجعي غير مناسب.

**تنبيه Data API حديث من Supabase**
- منذ 30 أكتوبر 2026، لم تعد جداول `public` الجديدة تُعرَض تلقائيًا عبر Data API/GraphQL. لذلك يجب التحقق من إعداد Exposed schemas في مشروع Production قبل الترقية، والتأكد من أن الجداول/الـViews المطلوبة للواجهة مكشوفة عمدًا، مع منح أقل صلاحيات لازمة وتفعيل RLS.
- لا يعني كشف الجدول منح صلاحيات صفوف؛ الوصول يتطلب إعداد التعريض وGRANT مناسبًا ثم اجتياز RLS. ولا يجوز حل مشكلة عدم الظهور بمنح `anon` أو `PUBLIC` وصولًا عامًا.
- لم يتم تغيير إعداد Data API أو أي GRANT في Test أو Production. هذا بند Preflight إلزامي قبل اعتماد حزمة SQL.

**ملاحظة تحديث CLI:** Supabase CLI v3 أصبح يستهدف البيئة المحلية افتراضيًا، ويحتاج `--remote` صريحًا عند التعامل مع مشروع مستضاف؛ كما يطلب تأكيدًا قبل تغييرات المشاريع المستضافة. لم نستخدم CLI أو ننفذ تغييرات مستضافة في هذه المرحلة.


### مراجعة القيود والفهارس والعدادات (25 نوفمبر 2026)

**نتائج القيود والفهارس للجداول السبعة في Test**
- `purchase_invoice_cost_snapshots`: المفتاح الأساسي `(invoice_id, product_id)` وفهرس على `product_id`.
- `stock_adjustment_cost_snapshots`: المفتاح الأساسي `(business_id, movement_id)` وفهارس على `movement_id` و`product_id`.
- `operation_counters`: المفتاح الأساسي `(business_id, operation_type)` وقيد `last_number >= 0`.
- `treasury_transfers`: مبلغ موجب، وسيلتا دفع مختلفتان ومن قائمة مسموحة، منع عكس السجل لنفسه، مفتاح فريد مركب `(business_id,id)`، كود فريد داخل النشاط، وفهرس فريد جزئي يمنع أكثر من عكس واحد للتحويل الأصلي. يوجد فهرس للتاريخ والمنشئ.
- `purchase_returns`: الإجمالي والرصيد الدائن غير سالبين، الحالة `posted/void`، رقم المرتجع فريد داخل النشاط، وفهارس للفواتير والمورد والحالة.
- `purchase_return_items`: الكمية موجبة، التكلفة والإجمالي غير سالبين، الحالة `good/damaged`، وفهارس للمرتجع وبند الشراء والمنتج.
- `customer_credit_ledger`: المبلغ غير صفري، أنواع الأحداث محصورة في `return_credit/invoice_application/payout/reversal`، مفتاح فريد مركب `(business_id,id)`، وفهرس فريد يمنع عكس الحدث أكثر من مرة، وفهارس العميل والمصدر والفاتورة والدفعة.
- الجداول السبعة عليها RLS. لا توجد سياسات كتابة مباشرة؛ سياسات القراءة في Test: snapshots للمالك فقط، مرتجعات المشتريات لمن لديه `purchases.view`، التحويلات لمن لديه `treasury_transfer.view`، دفتر رصيد العميل لمن لديه `sales.view` أو `parties.view`. جدول `operation_counters` بلا سياسة قراءة مباشرة ولا GRANT لأدوار التطبيق، والوصول للعدادات يتم من الدوال المخصصة.
- منح `anon` المباشرة لـSELECT على `purchase_returns`, `purchase_return_items`, `treasury_transfers` موجودة في Test رغم عدم وجود سياسة anon تسمح بصفوف. لا تُنسخ هذه المنح للإنتاج؛ امنح `authenticated` فقط حسب الحاجة وRLS.

**فجوات علاقات same-business المؤكدة**
- FK العكس في `treasury_transfers` وحده يستخدم `(business_id,reversal_of_transfer_id)` إلى `(business_id,id)`؛ بقية عدد من العلاقات تستخدم معرفًا منفردًا.
- روابط `purchase_returns` إلى الفاتورة والمورد، وروابط `purchase_return_items` إلى المرتجع وبند الشراء والمنتج، وروابط snapshots إلى المنتج/الفاتورة/الحركة، وروابط `customer_credit_ledger` إلى العميل/الفاتورة/الدفعة/مرتجع المبيعات لا تفرض جميعها تطابق النشاط ضمن FK.
- قبل إضافة مفاتيح مركبة، يجب التحقق من وجود unique key مطابق على الجدول المرجعي، وإضافة المفتاح المرجعي المركب الناقص عند الحاجة. لا تُطبّق هذه القيود قبل تدقيق أي بيانات قائمة، ومراعاة علاقات `payments` و`purchase_items` و`stock_movements` التي لا تملك حاليًا جميع المفاتيح المركبة المطلوبة.
- توجد Triggers حراسة على `payments.invoice_id` و`cash_transactions.invoice_id` تمنع ربط فاتورة من نشاط آخر. لا تعمم هذا الحارس على أعمدة متعددة الأنواع دون مراجعة دلالاتها.

**الترقيم وتهيئة operation_counters**
- `next_operation_code` يقفل العداد بقفل advisory لكل نشاط ونوع عملية، ثم يقفل صف العداد ويزيده. إذا لم يوجد صف، ينشئه بقيمة `count(*) + 1` من الجدول المقابل. الأكواد الناتجة تلحق الرقم بتاريخ القاهرة بصيغة `DDMMYY` دون فاصل.
- Triggers `assign_business_record_code` تولد أكواد الدفعات وحركات الخزنة والمصروفات والأطراف وحركات المخزون وتحويلات الخزنة ومرتجعات البيع/الشراء، حسب نوع العملية. Triggers منفصلة تولد أرقام فواتير البيع والشراء من أكبر لاحقة رقمية في أرقام الفواتير مع قفل advisory مستقل.
- الاعتماد على `count(*) + 1` عند غياب صف العداد ليس تهيئة آمنة عامة؛ عدد السجلات قد يختلف عن آخر رقم مستخدم. كذلك لا يمكن استخراج لاحقة العداد من الأكواد الحالية بصورة موثوقة بمجرد أخذ آخر مجموعة أرقام، لأن التاريخ والرقم متصلان بلا فاصل.
- لذلك يجب أن تكون تهيئة عدادات Production خطوة مستقلة قبل فتح أي كتابة جديدة: فحص الأكواد الحالية لكل نوع، ومقارنة أعداد السجلات والعدادات وسجل التدقيق، وتحديد قيمة بداية لا تعيد استخدام أي كود قائم. عند عدم إمكان إثبات القيمة الآمنة، يجب اعتماد قيمة بداية جديدة غير متعارضة بدل التخمين، مع اختبارها على Test أولًا. لا تنسخ صفوف عدادات Test إلى Production.
- في Test الحالي، أعداد السجلات والعدادات لا تتطابق دائمًا (مثل فواتير الشراء وحركات المخزون)، وهو دليل عملي على أن `count(*)` ليس مرجعًا موثوقًا لموضع العداد. لا تغيّر دالة الترقيم أو الأكواد القائمة في هذه المرحلة.
- لا توجد دوال `next_operation_code` أو Triggers الترقيم الجديدة في Production حتى الآن؛ لا تُنشأ قبل اكتمال حزمة الترقية واعتماد سياسة تهيئة العدادات.


### مطابقة Views بين Test وProduction والصلاحيات (25 نوفمبر 2026)

**Views المطلوبة للواجهة**
- Test يحتوي `cash_balances`, `product_stock_balances`, `party_account_balances`, `party_account_statement`, `customer_credit_balances`, `customer_credit_return_balances`، بالإضافة إلى `daily_business_summary`.
- Production يفتقد `customer_credit_balances` و`customer_credit_return_balances`، والـViews المشتركة أقدم في تعريفها.
- جميع الـViews التي فُحصت في Test وProduction تحمل `security_invoker=true`. يجب الحفاظ على هذا الخيار عند إعادة إنشاء/تحديث أي View؛ لا تحوّلها إلى Security Definer أو View بامتيازات المالك كحل بديل.

**الفروق الوظيفية المؤكدة**
- `cash_balances`: Test يحسب `account_method='cash'` فقط؛ Production يجمع كل وسائل الدفع في رصيد واحد. يجب اعتماد تعريف Test في الترقية حتى لا تختلط أرصدة النقدية مع التحويل البنكي وInstaPay والمحافظ.
- `product_stock_balances`: Test يفصل `sellable` عن `damaged` ويعرض `has_stock_history`, `out_of_stock`, `damaged_quantity`, `total_stock_quantity`. Production يجمع كل الحركات في كمية واحدة ولا يعرض هذه الحقول.
- `party_account_balances`: Test يخصم مرتجعات المشتريات من رصيد المورد ويعرض `purchase_returns_total` و`customer_net_collected`، ويفصل دفعات العميل المستقلة ودفعات المورد. Production لا يخصم مرتجعات المشتريات ويستخدم منطق دفعات أقدم.
- `party_account_statement`: Test يضيف `entry_timestamp`، ويعرض الدفعات المستقلة وعكوسها ومرتجعات المشتريات، ويستبعد المرتجعات الملغاة. Production لا يملك العمود أو هذه الدلالات الكاملة.
- `customer_credit_balances` و`customer_credit_return_balances` جديدتان في Test وتعتمدان على `customer_credit_ledger`; لا يمكن إنشاءهما قبل الجدول وسياسة قراءته.
- `daily_business_summary` في Test يستبعد المصروفات الملغاة والدفعات المرتبطة بمرتجعات ملغاة، ويفصل النقدية فقط في تدفقات الخزنة؛ Production أقدم ويحتاج مطابقة تعريفه كاملًا قبل نقله.

**الصلاحيات وRLS**
- Views في Test مثل `cash_balances`, `daily_business_summary`, `party_account_balances`, `party_account_statement`, `product_stock_balances` تمنح `anon` صلاحية على الـView، كما تمنح جداول أساسية متعددة `anon SELECT`. مع ذلك، هذه الجداول عليها RLS وسياسات القراءة فيها تعتمد على `has_business_permission`، بينما جداول الدفعات/المرتجعات الجديدة تستخدم سياسات `authenticated` صراحة. هذا ليس دليلًا وحده على تسرب صفوف، لكنه يمنح anon سطح وصول غير مطلوب ويجب تقييمه وإزالته من الحزمة الجديدة.
- Production لديه أيضًا منح `anon` على الـViews المشتركة الخمسة. لا تنسخ هذه المنح تلقائيًا عند إنشاء/تحديث Views؛ الهدف `authenticated` فقط، مع RLS على الجداول الأساسية، وبدون `PUBLIC` أو `anon` إلا إذا ثبتت ضرورة موثقة.
- `security_invoker=true` يجعل صلاحيات وسياسات الجداول الأساسية ذات صلة عند الاستعلام من الـView؛ لذلك يجب فحص GRANTs وRLS معًا، وليس الاكتفاء بوجود RLS.
- لم يتم تغيير أي View أو GRANT أو سياسة في Test أو Production خلال هذه المراجعة.

**ترتيب إنشاء/تحديث Views في حزمة الترقية**

### تدقيق القيود والعلاقات والصلاحيات للجداول السبعة (25 نوفمبر 2026)

تم استخراج القيود والفهارس وRLS والمنح مباشرة من قاعدة الاختبار، ومقارنتها بالإنتاج. الإنتاج لا يحتوي أيًا من الجداول السبعة حتى وقت الفحص، ولذلك لم تظهر قيود أو سياسات مقابلة هناك. المراجعة قراءة فقط.

**قيود وفهارس مؤكدة في Test**
- `operation_counters`: مفتاح أساسي مركب `(business_id, operation_type)`، وشرط `last_number >= 0`، وFK للنشاط.
- `purchase_returns`: مفتاح أساسي، وUnique على `(business_id,id)` و`(business_id,return_no))، وفهارس بحث حسب النشاط/الفاتورة/الحالة والمورد/الحالة، وقيود الحالة `posted/void` والمبالغ غير السالبة، وFKs للنشاط والفاتورة والمورد.
- `purchase_return_items`: PK، وقيود كمية موجبة وتكلفة/إجمالي غير سالب والحالة `good/damaged`، وفهارس للمرتجع وبند الشراء والمنتج، وFKs للمرتجع وبند الشراء والمنتج والنشاط.

- `customer_credit_ledger`: PK، وUnique `(business_id,id)` وUnique على `reversal_of_id` لمنع عكس مكرر، وقيود المبلغ غير الصفري ونوع الحدث، وفهارس العميل والمصدر والدفعة والفاتورة، وFKs للمراجع.
- جدولا snapshots: PKs مركبة وفهارس للمراجع، وFKs إلى الحركة/الفاتورة والمنتج.

**فجوات سلامة same-business تحتاج حسمًا قبل كتابة Migration**
- في `purchase_returns`، روابط الفاتورة والمورد هي FKs على المعرف فقط، وليست مركبة مع `business_id`.
- في `purchase_return_items`، روابط المرتجع وبند الشراء والمنتج هي FKs على المعرف فقط؛ لا يوجد FK مركب يفرض تطابق النشاط بين السطر والمرتجع/بند الشراء/المنتج.
- في `customer_credit_ledger`، روابط العميل والفاتورة والدفعة والمرتجع وسجل العكس هي FKs على المعرف فقط؛ يلزم تقييم فرض تطابق النشاط ونوع الطرف على مستوى قاعدة البيانات.
- في `purchase_invoice_cost_snapshots` و`stock_adjustment_cost_snapshots`، توجد أعمدة `business_id` لكن علاقات الفاتورة/الحركة والمنتج ليست جميعها FKs مركبة تربط النشاط بالمصدر.
- لا نضيف قيودًا مركبة قبل التحقق من وجود مفاتيح مرجعية فريدة مناسبة في الجداول الأم، ومن عدم وجود صفوف مخالفة، ومن عدم تغيير سلوك العمليات المعتمدة. المطلوب حاليًا توثيق الفجوة لا الادعاء بأن القيود أُنشئت.

**سياسات RLS والمنح في Test**

- `treasury_transfers`: SELECT لـ`authenticated` بشرط `treasury_transfer.view`.

RLS يقيّد الصفوف لكنه لا يلغي الحاجة إلى إزالة منح الوصول غير الضروري.

- عند وجود عداد، يزيده واحدًا. عند غياب العداد، يبدأ حاليًا من `count(*) + 1` لسجلات الجدول المعني.
- Triggers الموجودة في Test تشمل توليد أكواد الأطراف والدفعات وحركات الخزنة والمصروفات وحركات المخزون وتحويلات الخزنة. فواتير الشراء والبيع تستخدم Trigger مختلفًا لتوليد رقم الفاتورة.

**ملاحظة مهمة على تهيئة العداد**
- الاعتماد على `count(*) + 1` لا يضمن تجاوز أعلى رقم موجود إذا كانت هناك سجلات محذوفة أو أكواد مدخلة يدويًا/مستوردة أو فجوات في التسلسل.
- توجد Unique indexes على `(business_id, code)` للأكواد التشغيلية، لذلك قد يرفض الإدراج عند تصادم الكود، لكنه لا يحل سبب التصادم.
- لأن الكود يجمع تاريخ القاهرة مع رقم متزايد، يجب أن يبدأ العداد من قيمة تتجاوز أعلى لاحقة رقمية فعلية مستخدمة لكل نوع داخل النشاط، وليس عدد الصفوف فقط. يجب فحص صيغة الأكواد الحالية والاستثناءات قبل اعتماد SQL التهيئة.
- لا نهيئ أو ننسخ أي عدادات الآن؛ إعداد العداد في Production يجب أن يتم تحت قفل مناسب وبطريقة لا تعيد استخدام كود سابق.

**أرقام فواتير البيع والشراء**
- `assign_automatic_invoice_number()` يعمل كـTrigger function عادي (ليس SECURITY DEFINER)، ويستجيب فقط عندما تكون قيمة `invoice_no` هي `AUTO` أو `تلقائي`.
- يستخدم advisory transaction lock منفصلًا لكل نشاط ونوع فاتورة، ثم يحسب أعلى لاحقة رقمية موجودة ويضيف واحدًا. توجد Unique indexes على `(business_id, invoice_no)` في فواتير البيع والشراء.
- إعداد `search_path=public` موجود على هذه الدالة، لكنها ليست SECURITY DEFINER، وصلاحية EXECUTE المباشرة ظاهرة لـpostgres وservice_role فقط في ACL؛ التشغيل المعتاد يتم من Trigger.
- يجب الحفاظ على فصل آلية ترقيم الفواتير عن عدادات الأكواد التشغيلية وعدم دمجهما دون اختبار.

**صلاحيات الدوال**
- ACL الفعلي للدوال الثلاث التي فُحصت لا يمنح EXECUTE لـ`anon` أو `authenticated` أو `PUBLIC`؛ التنفيذ الظاهر لـpostgres وservice_role فقط. يستدعي Trigger الدالة المساعدة في سياق مالكها.
- عند إعداد Production، يجب التحقق من مالك كل Trigger function وEXECUTE ACL بعد النشر، وعدم منح هذه الدوال مباشرة لعملاء التطبيق.

**قرار الترقية**
- يلزم تعديل/إعادة بناء منطق التهيئة الأولية للعداد ليعتمد على أعلى كود مستخدم، مع معالجة الأكواد اليدوية والاستثناءات، قبل تفعيل Triggers الترقيم في Production.
- لم تُجرّب عملية إدراج فعلية ولم تُختبر التزامنية على بيئة اختبار مستقلة في هذه الجولة؛ النتائج مراجعة ساكنة للتعريفات والقيود فقط.


### متطلب مرتجعات المشتريات متعددة الفواتير وتتبع مصدر الكمية (طلب المستخدم 24 نوفمبر 2026)

**المشكلة التي وصفها المستخدم**
عند شراء المنتج نفسه في أكثر من فاتورة للمورد، تظهر كمية المخزون الإجمالية المتاحة وكأنها متاحة في كل فاتورة على حدة. مثال المستخدم: منتج موجود في 3 فواتير؛ كميات الفاتورتين الأولى والثانية استُهلكت في المبيعات، بينما الكمية المتبقية مصدرها الفاتورة الثالثة. المطلوب ألا تتكرر الكمية المتاحة نفسها عند اختيار كل فاتورة، وألا يُسجل المرتجع على فاتورة مصدر غير صحيحة.

**السلوك المطلوب**
- إمكانية عمل مرتجع واحد يضم كميات من أكثر من فاتورة شراء إذا كان المنتج نفسه موجودًا في هذه الفواتير.
- عرض الكمية القابلة للرد لكل بند شراء بعد خصم ما سبق رده وما تم استهلاكه من تلك الدفعة/الفاتورة، لا استخدام إجمالي مخزون المنتج نفسه لكل فاتورة.
- عند توزيع المرتجع على عدة فواتير، يُحفظ لكل جزء مرجع بند الشراء وفاتورة الشراء الأصلية الصحيحة، وتُحفظ أسعار/تكاليف كل مصدر حسب سجله.
- لا يُسمح بتجاوز المتبقي الفعلي من أي مصدر، مع مراعاة حالة المخزون (صالح/تالف) والمرتجعات السابقة والحركات اللاحقة.
- ينعكس كل جزء على فاتورة المورد وحسابه ومخزونه، وتظل تفاصيل المصدر ظاهرة في سجل المرتجع وكشف الحساب.
- لا يُفترض FIFO كقاعدة معتمدة لمجرد أنه اقتراح تقني سابق؛ يجب أن تكون طريقة تحديد مصدر الكمية مطابقة للمصدر الحقيقي الذي خرجت منه. إذا تعذر إثبات المصدر تاريخيًا، لا يخترع النظام نسبةً إلى فاتورة بعينها.

**نتيجة فحص التنفيذ الحالي في Preview/Test**
- واجهة مرتجع المشتريات تختار فاتورة شراء واحدة فقط في `purchaseReturnInvoice`.
- رأس `purchase_returns` يحتوي `purchase_invoice_id` واحدًا، ودالة `post_purchase_return_with_settlement` تنشئ مرتجعًا مرتبطًا بفاتورة واحدة فقط.
- عناصر المرتجع `purchase_return_items` تربط كل عنصر بـ`purchase_item_id`، والدالة تشترط أن يكون بند الشراء تابعًا إلى الفاتورة المختارة في رأس المرتجع.
- الواجهة تحسب المتاح لكل بند كأصغر قيمة بين كمية بند الشراء ناقص المرتجعات السابقة، وإجمالي مخزون المنتج المتاح في الحالة المختارة. لكن إجمالي المخزون محسوب على مستوى المنتج كله، وليس على مستوى دفعة/فاتورة الشراء؛ لذلك يمكن أن تظهر الكمية الإجمالية نفسها عند فتح فواتير شراء مختلفة للمنتج نفسه.
- دالة ترحيل فاتورة البيع تسجل `sales_items.product_id` والكمية وحركة مخزون عامة مصدرها فاتورة البيع؛ لا تسجل تخصيص كل وحدة مباعة على `purchase_item_id` أو دفعة شراء محددة. بالتالي لا يمكن للنظام الحالي معرفة أن الكمية المباعة استُهلكت من الفاتورة الأولى أو الثانية أو الثالثة على وجه اليقين.
- البنية الحالية لا تدعم مرتجع مشتريات واحدًا متعدد الفواتير، ولا تملك سجل تخصيص بيع إلى دفعات شراء. هذا متطلب غير منفذ، وليس مجرد تعديل عرض في الواجهة.

**المطلوب قبل تنفيذ المتطلب**
1. تصميم تتبع دفعات/مصادر المخزون وربط حركات البيع بتخصيص الكمية على بنود الشراء الأصلية، مع معالجة المخزون الافتتاحي والتسويات والمرتجعات والتحويل بين صالح/تالف.
2. تحديد قاعدة تخصيص المصدر عند البيع والمرتجعات القديمة التي لا تملك تخصيصًا تاريخيًا؛ لا يجوز اختلاق المصدر بأثر رجعي. أي قاعدة افتراضية مثل FIFO تحتاج اعتمادًا واضحًا قبل التنفيذ.
3. تعديل نموذج رأس المرتجع ليسمح بأكثر من فاتورة مصدر عند الحاجة، أو اعتماد رأس مرتجع واحد مع عدة مراجع فواتير وبنود، مع ضمان تسوية حساب المورد والفواتير بدقة.
4. مراجعة الإلغاء والعكس والتكلفة المتوسطة وتقارير المخزون وكشف حساب المورد، بحيث تعكس كل تخصيص مصدره ولا تسمح بعكس غير آمن.
5. اختبار حالات: نفس المنتج في عدة فواتير بتكاليف مختلفة؛ بيع جزئي/كامل من دفعات مختلفة؛ مرتجعات سابقة؛ صالح/تالف؛ مرتجع يجمع عدة فواتير؛ إلغاء المرتجع؛ وحركات مخزون لاحقة.

**حالة المتطلب**
مسجل كمتطلب معتمد للمراجعة المستقبلية فقط. لم يتم تعديل الواجهة أو قاعدة البيانات لتنفيذه، تماشيًا مع قرار المستخدم الحالي بإيقاف التعديلات الوظيفية والتركيز على التحقق والترقية. لا تنقل أي بيانات أو تخصيصات تاريخية مفترضة إلى Production.

### فحص مفاتيح الجداول الأم المطلوبة لعلاقات same-business (25 نوفمبر 2026)

تمت مقارنة الفهارس الفريدة على الجداول الأم في Test وProduction. هذا فحص كتالوج فقط، لا تعديل.

- `purchase_items(business_id,id)` غير موجود حتى في Test؛ لا يمكن بناء FK مركب إليه قبل إضافة Unique مناسبة.

**النتيجة**
- لا يكفي إضافة FK مركب في الجداول الجديدة وحدها. يجب أولًا إضافة Unique indexes مركبة على الجداول الأم التي تسمح بذلك، بعد فحص البيانات والتكلفة التشغيلية.

- الجداول الموجودة في Production تحتوي صفوفًا تشغيلية قليلة وقت خط الأساس، لكن لا يُستنتج من ذلك إمكانية تجاوز فحص التكرارات أو قفل الجداول عند إضافة الفهارس.
- لا توجد بيانات من Test ستُنقل إلى Production، ولا تُنفذ أي إضافة فهارس ضمن هذه الجولة.
