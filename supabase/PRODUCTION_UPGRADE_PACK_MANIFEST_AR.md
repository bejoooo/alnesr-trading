الفرع الأصلي غير المعدّل: `development`

## قواعد لا تتغير

- هذه الحزمة للمراجعة والتحضير فقط؛ لا تشغّل أي ملف SQL قبل موافقة منفصلة وصريحة على التنفيذ المحدد.
- لا تُشغّل أي Migration أو DDL/DML على Production أو Test الحالية خلال التحضير.
- لا تنقل بيانات تشغيلية من Test إلى Production.
- Production تحتفظ بسجل النشاط وعضوية المالك. لا Reset ولا حذف للنشاط أو العضوية.
- لا تغيّر واجهة Preview ولا صيغة التكلفة التي اختبرها المستخدم. يجب نقل سلوك Test كما هو.
- لا تستخدم service_role key في المتصفح.
- لا تدمج هذا الفرع في development أو main تلقائيًا.

## نقاط تحقق قبل اعتماد أي ملف

1. تأكيد أن جميع المتطلبات السابقة موجودة وأن أنواع الأعمدة والتواقيع تطابق Test.
2. فحص أي أكواد/قيود حالية وتكرارات قبل إنشاء الفهارس الفريدة.
3. التحقق من عدم وجود روابط بين نشاطين قبل اعتماد FKs المركبة.
4. مطابقة RLS وACL وSECURITY DEFINER وsearch_path لكل RPC.
5. فحص الصيغ المحاسبية: لا تُعدّل طريقة التكلفة المختبرة؛ قارن تعريفات Test ولا تعِد صياغتها.
6. مرحلة 5B لا تخترع أكوادًا أو أسعارًا؛ تتوقف إذا ظهر سجل بلا كود أو بلا بند بيع أصلي يمكن أخذ سعره منه.
6. لا تعتبر نجاح فاحص الكتالوج أو المراجعة الساكنة اختبارًا وظيفيًا.

## حدود الاختبار المتاحة حاليًا

- Test الحالية تحتوي بيانات اختبار يريد المستخدم الاحتفاظ بها للمقارنة، ولذلك تظل قراءة فقط.
- Production ليست بيئة اختبار؛ يجب الحفاظ على النشاط وعضوية المالك فيها.
- لم يتم حتى الآن توفير نسخة محلية معزولة مؤكدة التشغيل مع PostgreSQL وبدائل Auth/Storage. لا يُدّعى نجاح functional tests قبل توفيرها.
- النسخة الاحتياطية بصيغة custom dump قابلة للقراءة عبر `pg_restore --list`، لكن لم يُجرَ restore تجريبي بعد.

## سجل التغييرات في هذا الفرع

- إصلاح خطأ dollar-quoting في أول كتلتين PL/pgSQL في ملف العلاقات المركبة.
- إضافة أربعة روابط مركبة same-business: purchase_return_id وsales_return_id في payments وcash_transactions.
- إضافة مسودة الفهارس وقيود CHECK الناقصة.
- إضافة مسودة ACL ضيقة لعمود businesses.tagline وسياسة payments_read.
- إضافة مرحلة نهائية محمية لاشتراط الأكواد وسعر بند المرتجع بعد وجود Triggers، مع backfill من sales_items.unit_price فقط عند تطابق business_id وsales_item_id.
- تحديث بوابة متوسط التكلفة: المستخدم أكد اعتماد منطق Preview المختبر دون تغيير.
- أضيفت دالة `reset_business_data(uuid)` إلى دفعة Owner Actions بعد اكتشاف أن Preview تستدعيها؛ الإضافة تعريف فقط ولا تنفّذ التصفير. يلزم قبل Go-Live حسم حماية التأكيد على مستوى الخادم، لأن فحص كلمة المرور وعبارة التأكيد حاليًا في الواجهة فقط.
- لا توجد تغييرات على قواعد البيانات أو Auth أو Storage أو Edge Functions أو ملفات الواجهة.


### بوابة أمان محدثة — مراجعة SECURITY DEFINER — 27 نوفمبر 2026

- تمت مراجعة 53 دالة SECURITY DEFINER في Test: 48 قابلة للتنفيذ بواسطة authenticated، وصفر قابلة للتنفيذ بواسطة anon. الاستثناء الوحيد الذي لا يحتوي auth.uid() مباشرة هو wrapper للمبيعات ذات 9 معاملات، ويفوض إلى نسخة 10 معاملات التي تتحقق من الهوية والصلاحية.
- **خيار تصفير البيانات ما زال مانع Go-Live:** كلمة المرور وعبارة التأكيد مفحوصتان في الواجهة فقط، بينما RPC تقبل استدعاء مباشر من جلسة المالك وتتحقق من دوره النشط فقط. يجب تعطيل الخيار قبل الإطلاق أو اعتماد تأكيد خادمي أحادي الاستخدام. لم يتم تنفيذ تغيير أو استدعاء RPC.


### فروق صلاحيات Preview مقابل Test — تنبيه قبل حسابات الموظفين

مقارنة أجسام RPC كشفت 4 اختلافات موثقة في `get_treasury_balances` و`record_invoice_payment` و`record_standalone_party_payment` و`post_purchase_with_method`. مسودات الترقية الحالية تتبع شروط الواجهة الحالية في Preview، بينما بعض دوال Test تستخدم شروطًا مختلفة (خاصة cash.withdraw مقابل cash.create، وtreasury_transfer.view مقابل cash.view + payments.view). لا تغيّر هذه المسودات الواجهة، ولا يوجد موظفون حاليًا؛ يجب حسم سياسة التفويض واختبارها بحسابات أدوار قبل إنشاء حسابات موظفين.

### تحديث مسار الاختبار المحلي — 27 نوفمبر 2026

- راجعت محتويات مجلد `supabase/` في الفرع التحضيري: لا يوجد حاليًا `config.toml` أو `config.json` أو `config.jsonc`، ولا يوجد إعداد Local Supabase جاهز أو مجلد migrations قياسي؛ ملفات SQL الحالية مرقمة مباشرة داخل `supabase/`.
- النسخة الاحتياطية المحفوظة هي Custom archive ناتجة عن `pg_dump -Fc`. توثيق Supabase CLI يصف وسيط `supabase db start --from-backup` بأنه يقبل «logical backup file»، لكنه لا يحدد في المرجع المفتوح صراحةً تنسيق Custom archive أو خيارات الاستعادة؛ لذلك لا نجزم بعدم توافقه ولا نشغّله قبل اختبار نسخة إضافية من الملف محليًا والتحقق من إصدار CLI وسلوكه. لا تستخدم الملف الأصلي مباشرةً في التجربة.
- مسار الاختبار الآمن المحتمل: إنشاء مشروع Supabase محلي مؤقت في مجلد منفصل عن المستودع، وتشغيله على Windows باستخدام Docker Desktop، ثم تقييم استعادة الـCustom archive إلى قاعدة محلية منفصلة باستخدام `pg_restore` بعد فحص قائمة TOC والاعتماديات والأدوار والامتدادات. لا يُنفذ هذا قبل تحديد طريقة استعادة متوافقة مع مخططات Supabase المحجوزة مثل `auth` و`storage` و`vault`.
- تثبيت PostgreSQL 17.12 وحده يوفّر أدوات `pg_dump/pg_restore` لكنه لا يشغّل خدمات Supabase المحلية (Auth/Storage/API). يلزم Docker Desktop أو runtime متوافق على Windows لتشغيل Local Supabase Stack بالطريقة القياسية.
- تنبيه CLI: تغيّر Supabase CLI v3 في نوفمبر 2026 بحيث تستهدف أوامر قواعد البيانات البيئة المحلية افتراضيًا، وتحتاج `--remote` صراحةً للوصول إلى مشروع مستضاف. كل أوامر الاختبار المقترحة يجب أن تبقى محلية، ويُمنع إضافة `--remote` أو ربط المجلد المؤقت بمشروع Production.
- لم يتم تثبيت CLI أو Docker، ولم يتم تشغيل أي استعادة أو SQL نتيجة هذه المراجعة. لا توجد تغييرات على Test أو Production.

- تصحيح توثيقي: وصف عدم توافق ملف `.dump` مع `--from-backup` كان جازمًا أكثر من الأدلة المتاحة. المرجع الرسمي يقول «logical backup file» دون توضيح كافٍ للتنسيق؛ يلزم إثبات عملي على نسخة منفصلة قبل اعتماد المسار.
