# واجهة النسر للتجارة

واجهة عربية RTL متجاوبة لإدارة النشاط، مجهزة كـ PWA قابلة للتثبيت على Windows وAndroid وiPhone. هي ليست تطبيقًا أصليًا Native حتى الآن.

## ما تم تجهيزه

- تسجيل الدخول وإنشاء الحساب واستعادة الجلسة عبر Supabase Auth.
- إنشاء نشاط وربطه بالمستخدم المنشئ كمالك، وتحميل العضويات واختيار النشاط عند تعدد الأنشطة.
- كتالوج المنتجات: الإضافة والتعديل والبحث والتصفية والأسعار والضمان والمواصفات والصور.
- فصل كتالوج المنتجات عن المخزون الفعلي؛ إضافة المنتج وحدها لا تنشئ كمية مخزون.
- تسويات المخزون وسجل الحركات.
- الموردون والمشتريات متعددة البنود، وإضافة منتج جديد داخل فاتورة الشراء، وتوزيع خصم المورد، والدفعات الجزئية وكشف الحساب.
- العملاء والمبيعات متعددة البنود والخصومات والتحصيلات الجزئية وكشف الحساب وطباعة الفاتورة.
- المرتجعات المرتبطة بالفاتورة الأصلية، مع تحديد الصالح والتالف وتسوية المستحق أو رد النقد.
- الخزنة: الرصيد الافتتاحي والإيداع والسحب والمصروفات وسجل الحركات.
- الأرصدة الافتتاحية للعملاء والموردين.
- إعدادات النشاط وإدارة الموظفين وصلاحياتهم؛ إدارة الموظفين محصورة في المالك.
- تقارير المبيعات والمشتريات والتحصيلات والمدفوعات والمصروفات والخزنة والمرتجعات والمخزون وحسابات الأطراف، مع تصدير XLSX.
- نسخة احتياطية JSON واستعادة آمنة إلى نفس النشاط بشرط أن تكون جداول البيانات المستهدفة فارغة، وبصلاحية المالك فقط.

## ربط الاختبار الحالي

- ملف `app/config.js` مربوط بمشروع Supabase التجريبي `alnesr-trading-test`، ويحتوي فقط على بيانات اتصال العميل العامة.
- قاعدة الاختبار تعمل، واجتاز `verify_setup.sql` فحص التحقق الهيكلي.
- ملفات SQL من `schema.sql` و`002` حتى `029` موجودة في المستودع، وطُبقت التغييرات المطلوبة على قاعدة الاختبار. بعض الملفات القديمة مثل `012` و`014` نُفذت سابقًا يدويًا من SQL Editor، لذلك قد لا تظهر كسجلات مستقلة في migration ledger.
- تم اختبار عمليات الشراء والبيع والدفعات والمرتجعات والمخزون والخزنة والمصروفات في معاملات مؤقتة تم التراجع عنها. كما تم اختبار إعادة حساب متوسط التكلفة عند المرتجع الصالح.
- فحوص الصلاحيات أكدت أن جميع جداول `public` عليها RLS، ولا توجد صلاحيات API مباشرة للحذف أو TRUNCATE أو الكتابة المباشرة على دفاتر العمليات المحاسبية.
- صور المنتجات محفوظة في bucket خاص، بحد 5 ميجابايت وأنواع JPG/PNG/WebP.

## ما لم يتم التحقق منه بعد

- لم يكتمل اختبار الواجهة داخل متصفح فعلي على هاتف وكمبيوتر.
- لم يُختبر حساب موظف منفصل فعليًا؛ النشاط التجريبي يحتوي حاليًا على المالك فقط.
- لم يُختبر مسار إضافة موظف ببريد مستخدم آخر وتغيير صلاحياته من الشاشة.
- لم تُختبر كل حالات الواجهة والطباعة والتصدير على أحجام شاشات وأجهزة مختلفة.
- النسخة الاحتياطية JSON لا تتضمن سجل التدقيق ولا الملفات الثنائية لصور المنتجات داخل Storage؛ يلزم الاحتفاظ بنسخة مستقلة من الصور.
- التقارير تعرض بعض الأرصدة الحالية، ولا تمثل بالضرورة لقطة تاريخية للأرصدة كما كانت في نهاية فترة سابقة. كما أن بعض هوامش الربح المعروضة تقديرية.

## النشر

التطوير الحالي موجود على فرع `development-v1-updates`، وهو منفصل عن `main`. لم يتم دمج التطوير أو نشره إلى GitHub Pages بعد. لا تعتبر النسخة المنشورة حاليًا هي النسخة الأحدث حتى يتم اعتماد الدمج والنشر بعد الاختبار الشامل.

## إعداد مشروع Supabase جديد

1. أنشئ مشروع Supabase جديدًا للاختبار وانتظر حتى يصبح نشطًا.
2. شغّل `supabase/schema.sql` ثم ملفات `002` حتى `011` بالترتيب الرقمي، وبعدها شغّل `supabase/verify_setup.sql`.
3. طبّق ملفات `012` حتى `029` بالترتيب، بعد مراجعة كل ملف.
4. ضع Project URL ومفتاح العميل العام فقط في `app/config.js`.
5. انشر مجلد `app` على استضافة HTTPS، ثم اختبر تسجيل الدخول وإنشاء النشاط وكل العمليات بحسابات تجريبية.

**مهم:** لا تضع مفتاح `service_role` أو أي مفتاح سري في ملفات الواجهة أو GitHub. لا تُعد تشغيل ملفات التأسيس على قاعدة بيانات تحتوي بيانات فعلية، ولا تستخدم النظام تجاريًا قبل إتمام اختبار المتصفح والصلاحيات بحسابات منفصلة.
